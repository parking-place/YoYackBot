- 관점: 이 서비스가 **계속 안정적으로, 감당할 비용(모델 할당량)으로** 돌 수 있는가. 제품·UX, 기능·커뮤니티, 품질·안전·개발 프로세스는 다른 검토자가 맡는다.

## 한 줄 결론

**코드 안쪽의 방어(격리 실행·상한·worker 감독·민감정보 없는 구조화 로그)는 탄탄하다. 하지만 코드 밖 운영 층은 비어 있다. 알림, 자동화된 배포·롤백, 할당량 통제, 모델 엔진 교체 수단이 없다.** 그래서 계정 하나, 모델 하나, CLI 파일 하나, LXC 한 대 가운데 어느 하나만 흔들려도 **사용자가 먼저 장애를 알아채고, 운영자가 손으로 복구**해야 한다.

## 강점

1. **격리된 모델 실행**: bwrap 최소 마운트, 네트워크·도구 차단, 인증 사본과 비교 후 교체(CAS) 방식의 토큰 갱신, 프로세스 그룹 강제 종료(`codex_runner.py:136-171,250-274,340-384`). 장애가 나도 비밀값이나 원문이 새지 않게 설계됐다.
2. **자원 상한이 설정으로 분리됨**: 동시 실행 4 상한, 유한 대기열과 대기 시간, 입력·출력 바이트, 호출 timeout, 출력 스트림 5 MB 상한(`config.py:111-118`, `job_queue.py:42-111`, `codex_runner.py:28`).
3. **수집 worker 감독과 상태 구분**: 감독 루프의 재시작·backoff, 15분 정체 감지, `health`의 process/gateway/worker/local 분리(`discord.py:514-551`, `health.py:11-14`, `__main__.py:115-132`). 이전 검토의 B05를 해소했다.
4. **민감정보 없는 구조화 지표**: 허용 목록 기반 JSON 로그, 호출별 소요 시간·토큰·강도(`ops.py:43-101`, `timing.py:63-87`). 비용·병목 분석의 토대가 이미 있다.
5. **꼼꼼한 출시 증거와 복귀 호환 확인**: 정확한 SHA, wheel/tar sha256, 후보 venv 회귀, 중지 전 온라인 백업, **이전 wheel이 새 DB를 읽는지 확인**, 못 본 항목은 NOT_RUN으로 기록(`evidence/1.4.4c-P2.md:15-28`). schema 5에 선택 테이블만 더하는 방식이라 복귀에 마이그레이션이 필요 없다(`watch_store.py:137`).
6. **실행 중 성능 저하 모드**: 엔진 생성이 실패하면 요약 대신 안내를 보내고 수집은 계속한다(`discord.py:1460-1476`). 아래 OP-02처럼 systemd 설정이 이를 막고 있을 뿐이다.

1. **알림 1차**(OP-I01 일부): `health`를 부르는 systemd timer와, 실패하면 webhook 한 줄을 보내는 `OnFailure=` unit을 둔다. 코드 변경은 없고 unit 파일 2–3개면 된다.
2. **재시작을 포기하지 않기**: `StartLimitBurst`·`StartLimitIntervalSec`를 조정하고 `RestartSteps`/`RestartMaxDelaySec`를 쓴다(Debian 13 systemd에서 지원, 추정).
3. **기동 게이트 완화**(OP-I02 최소안): `ExecStartPre`를 DB·입력 검사 전용 옵션(예: `check-ready --local`)으로 바꾼다. 런타임 성능 저하 경로(`discord.py:1460-1476`)는 이미 있다.
4. **실패 종류 로그**: 사자성어·셀프디스·식단·주간·안내 실패 로그에 `CodexRunError.kind` 값을 붙인다. 고정 분류라서 개인정보 위험이 없다.
5. **`model_call` 한 줄**: `codex_engine._execute`에서 호출 이름·모델·ms·결과 종류·토큰을 남긴다. 사진 호출 비용이 바로 보인다.
6. **배포 체크리스트 두 줄 추가**: 진행 중 작업 확인에 셀프디스·식단·안내를 넣고, 20:50–23:10 배포를 금지한다.
7. **빠른 모드 전역 차단 스위치**와 **`USAGE_LIMIT` 차단기**: 환경 변수 하나와 모듈 상태 하나면 된다.
8. **문서 드리프트 정리**: `observability.md:15`, `restore.md:3`, `handoff-1.0.0.md:13`.

## 검토 한계

- 정적 검토만 했다. 운영 LXC의 실제 설정(환경 변수, journald 적용 여부, 배포 템플릿, 백업 파일 위치), 현재 DB 크기, 실제 사용량 추이, Discord 포털 설정(공개 봇 여부·intent)은 확인하지 않았다. 이에 기댄 판단은 "추정" 또는 조건부로 적었다.
- 토큰·호출 수는 과거 증거(1.3.3 합성 평가)와 코드상 상한에서 계산했다. 식단(사진) 호출의 실제 토큰은 기록이 없어 추정조차 하지 못했다. 이 공백 자체가 OP-07이다.
- 할당량 정책(5시간/주간 창의 소모 단가, 빠른 모드 배율, 계정 등급)은 공급자 측 사항이라 검증하지 않았다.
- 테스트 실행, 부하·장애 주입, 실제 모델 호출은 하지 않았다. 테스트 신뢰성·간헐 실패(`evidence/1.4.4c-P2.md:18`)와 보안 세부는 품질·안전 검토자 몫으로 남긴다.
