# 04. 구조·운영·품질 개선

기준: `5f85734`. 아래는 개선 권고이며 기존 개발 단계나 출시 판정을 변경하지 않는다.

## 구조: 현행 경로를 기준으로 책임을 정리할 필요

`discord.py` 795행은 명령 응답뿐 아니라 백필 스케줄, 재접속, 보존 정리, heartbeat, 역할 삭제까지 담당한다. 크기 자체보다 **각 background task의 생성·실패·복구 정책이 어댑터 안에서 흩어진 점**이 문제다. 백필 수명 관리자, 명령 처리, 데이터 이벤트 처리를 책임별로 나누되 현재 공개 동작을 유지하는 방향이 적절하다.

`domain.py`에 Protocol이 있지만 `SummaryWorkflow`의 필드는 구체적인 수집기·엔진·게시기에 결합되어 있다. 현재도 fake로 테스트할 수 있으나, 프로토콜과 실제 생성 경로가 일치하도록 정리하면 대체 구현과 실패 주입의 범위가 명확해진다.

예전 `TimeRangeCollector` 계열과 현행 `CacheOnlyCollector`를 즉시 삭제할 필요는 없다. 우선 사용처·지원 상태를 표시하고, B03 같은 보호 로직이 어느 경로에 적용되는지 명시해야 한다. 실사용 경로를 바꾸는 PR에는 `build_workflow()`로 만든 객체를 통한 수집·요약·게시 통합 회귀가 필요하다.

메시지 적격성 판정도 신규·수정·History에서 공유하는 것이 좋다. 신규·History 경로는 명령을 제외하지만 `on_message_edit → on_watched_message`는 명령 파싱 없이 저장한다(`discord.py:440–448,510–587,642–665`, `backfill.py:370–375`). 캐시된 봇 명령의 편집본이 대화에 들어갈 수 있는 정적 후보이며, 수정 전후에 명령 여부가 바뀌는 정책을 먼저 정해야 한다.

## 성능과 공정성

| 관측한 구조 | 문제·조건 | 개선 및 측정 기준 |
|---|---|---|
| 기간형 `recent().fetchall()` | 입력 한도 전에 전체 메모리 적재(B08) | 배치 cursor로 읽고 budget 초과 즉시 실패; peak RSS와 읽은 행 수 측정 |
| 설정 callback의 동기 SQLite | writer 잠금이 Gateway 전체 지연(B09) | 응답 defer, 비동기 어댑터 또는 thread; 잠금 중 이벤트 루프 tick 측정 |
| `pending()`의 전역 `LIMIT 20` | 먼저 등록한 Guild의 20개 장기 백필이 후발 Guild를 후보에서 제외 | DB 후보 선택부터 Guild별 회전·quota; 20개 대 1개 사례의 첫 처리 지연 측정 |
| 사용량 lock | 동시 실행만 제한하고 대기 요청 수·시간은 제한하지 않음 | 짧은 TTL 캐시, 진행 중 조회 공유, 대기 상한 |
| 상태마다 CLI 버전 subprocess | 반복 조회가 비싼 프로세스 생성을 유발 | 고정 실행파일 fingerprint 기반 캐시와 강제 새로고침 |
| 실패 후 즉시 재요청 가능 | 성공 쿨타임만 있어 의도적 실패 요청이 비용을 반복 발생시킬 수 있음 | 성공 쿨타임과 별개의 사용자/Guild 요청량 제한·실패 backoff |

공정성 근거: `backfill.py:58–69,176–185`, `discord.py:355–363`. 현재 round robin 테스트는 이미 여러 Guild가 포함된 리스트를 입력하므로 SQL LIMIT 이전 문제를 검증하지 않는다. 후발 Guild가 영구히 굶는다고 단정하지 않는다. 앞선 채널 완료·defer까지 대기가 길어지는 구조다.

사용량·상태 근거: `discord.py:607–615,630–638`, `usage.py:161–193`, `codex.py:46–54`. 실제 공격 부하나 OOM은 실행하지 않았다. 비동기·병렬 동작의 실제 자원 곡선은 별도 운영 환경 검증 대상이다.

## 운영: 연결 상태와 서비스 능력을 구분

현재 heartbeat는 프로세스와 Gateway 연결, 준비 검사는 로컬 DB·CLI·인증 파일 상태를 나타낸다. 이것만으로 백필 worker가 살아 있고 데이터가 최신이며 다음 모델 호출도 성공할 것이라고 말할 수 없다. B05처럼 worker만 종료될 수 있고, `authentication_ready()`는 JSON이 dict인지 확인하는 수준이다.

다음 상태를 서로 구분해 노출할 것을 권한다.

- 프로세스 생존과 Gateway 연결.
- 백필·정리 worker 생존, 마지막 성공·진척 시각.
- 채널별 최초 수집/공백 보충/차단 상태와 검증 완료 경계.
- 모델의 마지막 성공·실패 종류와 시간. 매 health 검사에서 유료 호출하지 않는다.
- 실행 중·대기 요청 수, 가장 오래 기다린 시간.

외부 자동 알림은 기존 운영 문서에서도 미구축 상태다. 먼저 로컬 상태의 의미를 정확히 만든 뒤 연속 실패나 worker 중단에만 경고하도록 설계해야 한다. 이 감사에서 알림 서비스나 자동화는 만들지 않았다.

게시 성공과 cooldown DB 쓰기는 하나의 트랜잭션으로 묶이지 않는다(`workflow.py:244–248`, `state.py:103–117`). 게시 직후 DB 쓰기 실패·프로세스 종료가 있으면 성공 결과는 남고 재요청은 가능해진다. 이는 외부 API와 DB의 경계다. 성공한 메시지 receipt와 요청 식별자를 제한적으로 보존해 재시도 여부를 안내하는 방향을 검토하되, 과거 내용을 자동 재전송하거나 모든 원문을 보관하는 방식은 피해야 한다.

## 품질: 문자열 검증과 사실 검증을 분리

`output_quality.py`는 표기·실패 표식·일부 표현을 검사할 수 있지만, 실제 화자 귀속·날짜·결정·인용의 사실성은 보장하지 않는다. 인용·코드에서 혐오어를 제외하는 규칙도 “원문에 존재하는 인용인가”를 검증하지 않는다.

합성 fixture 평가를 다음 축으로 나누는 편이 유용하다.

| 평가 축 | 필요한 실패 사례 |
|---|---|
| 범위 충실도 | 요청 밖 메시지 혼입, 누락된 구간을 완전한 요약처럼 표시 |
| 화자 귀속 | 동명이인, 닉네임 변경, 답글 관계, 중첩 Markdown의 내부 키 |
| 사실성 | 날짜·숫자·잠정 의견을 확정 사항으로 바꾸는 경우 |
| 결론과 진행 상태 | 미정 대화를 결정으로 서술하거나 미정 자체를 비웃는 경우 |
| 직접 인용 | 원문에 없는 발언을 화자에게 귀속 |
| 추가 요청 | 표현·길이 변경은 따르되 사실·보안 규칙은 유지 |
| 비용·지연 | 본문 재시도, 평가 재시도, 실패 시 전체 호출 수와 p95 지연 |

1.2.0은 호출 상한을 3번에서 5번으로 늘리는 계획이다. 기존 기본 동시 실행 4와 결합했을 때 처리시간·계정 한도·대기열 효과를 측정해야 한다. 현재 코드에서 5회 호출이 구현됐다고 판단하지 않는다.

## 테스트와 CI의 개선 방향

기존 1,178개 회귀와 Ruff는 통과했다. 그 결과는 가치가 있지만 다음 공백을 메우지 못한다.

1. **여러 수신자의 권한:** 요청자만 보는지 확인하는 검사와 공개 응답을 읽는 모든 사람의 권한은 다르다(B01).
2. **시간을 움직이는 재시작:** store 재생성만으로는 overlap의 종료 경계를 지난 실제 공백을 만들지 못한다(B04).
3. **복구 경로의 실패:** 정상 실패를 기록하는 DB 작업도 실패하도록 주입해야 한다(B05).
4. **현행 출력 형식:** 옛 단일 Markdown 패턴뿐 아니라 현재 프롬프트가 요구하는 형식을 검사해야 한다(B10).
5. **최종 합성 결과:** 첫 모델 응답, rating-only 응답, 평가 제거 후 본문, 최종 게시 결과를 같은 계약으로 검증해야 한다(B11·B12).

매 문구를 더 많이 고정하는 것보다 위 경계의 회귀를 추가하는 편이 우선이다. parser·Unicode 분할·interval·timestamp 순서에는 속성 기반 시험을 검토할 만하다. 커버리지 수치는 이번에 측정하지 않았으므로 “커버리지가 높다”는 평가는 하지 않는다.

## 문서와 출시 기록의 정합성

- `1.1.3a/STATUS.md:3`은 3단계 완료·출시를 선언하면서 같은 문장에 현재 출시 코드를 `v1.1.3`이라고 적는다. 여러 버전 STATUS에도 작성 당시 표현이 남아 있다. **출시 당시 기준**과 **현재 상태**를 분리할 필요가 있다.
- `docs/handoff-1.0.0.md`, `docs/security-review-0.8.0.md`의 7일 보관은 역사적 기록이고 현재 기본값은 30일이다. README가 최신 운영 진입점과 역사적 증거를 구분하도록 하는 것이 좋다.
- README의 11개 버전·55단계는 최초 0.0.0~1.0.0에 한정된다. 이후 버전까지의 전체 진행률로 읽히지 않게 범위를 붙이는 것이 좋다.
- `scripts/verify_repo.py`는 버전·단계 수를 직접 열거한다. 현재 출력은 1.1.3a까지 검증하며, 1.2.0의 6단계 의미적 정합성이나 STATUS의 모순된 문장은 검증하지 않는다. 선언형 버전 목록을 읽는 검사와 “구현·증거·종료” 상태 검사를 분리할 수 있다.
- source SHA, 패키지 버전, 설치 wheel, 운영 버전의 대응 관계를 하나의 작은 release manifest로 제공하면 checkout과 설치본이 다른 사고를 줄일 수 있다.

이 항목들은 수정 제안으로만 남겼으며, 원래 계획·운영 문서나 검사 스크립트를 고치지 않았다.
