# 05. 추가 기능 제안

기준: `5f85734`. 아래 항목은 제품 제안이며 새 개발 계획·일정·착수 승인이 아니다. 규모는 현재 구조 기준의 상대적 판단(S: 국소 변경, M: 여러 계층 변경, L: 데이터·운영 정책까지 변경)이다.

## 기존 계획과 구분

`Plans/0.DevelopPhase/1.2.0/CONTRACT.md`에는 이미 서버별 `/말투`, 답장 메시지부터의 요약 범위, 평가 후보 10개·모델 심사, 최근 평가 20개 기억, 최대 5회 호출이 들어 있다. 이들은 **기존 PLANNED 기능**이며 아래 신규 아이디어에 중복 계산하지 않았다.

또한 해당 계약의 “말투는 1,500자·빈 값만 검사”, “답장과 범위가 함께 있으면 답장 우선”, “도움말 그대로”라는 사용자 결정은 존중한다. 이번 문서에서 이를 바꾸거나 위험 문구 저장 차단을 필수 조건으로 추가하지 않았다. 대신 구현 시 고정 규칙의 우선순위, 저장 권한, 최종 출력 검증, 실제 공격성 평가를 확인할 것을 권한다.

## 추천 기능

| 제안 | 사용자 가치 | 최소 범위·제약 | 규모 | 우선순위 |
|---|---|---|---|---|
| F01. 비공개 운영 조회 | 주시 목록·수집 상태를 다른 사람에게 노출하지 않고 확인 | ephemeral 조회; 텍스트 명령 공개 응답 정책은 명시. B01 해소와 연결 | S~M | 높음 |
| F02. 수집 진행·차단 원인 | “아직 준비 중”이 얼마나 진행됐는지 이해 | 단계, 처리 페이지/건수, 마지막 진척, 권한·재시도 상태. 계산 근거 없는 ETA 금지 | M | 높음 |
| F03. 요청 취소·대기 상태 | 실수한 대량 요청을 취소하고 자원 회수 | 요청자 또는 관리자의 취소; 대기열·모델·임시 파일 함께 정리; 게시된 조각 자동 삭제는 별도 정책 | M | 높음 |
| F04. 원문 근거로 이동 | 중요한 날짜·결정·발언을 확인 | 주장별 근거 메시지 ID를 검증하고 링크 생성; 원문 범위·채널 권한 유지; 삭제된 근거 처리 | M~L | 높음 |
| F05. 보존·삭제 관리 | 무엇을 저장하는지 관리자가 이해하고 통제 | 현재 retention·정리 시각 표시, 특정 채널 캐시 지우기, 이후 재수집 여부 선택 | M | 높음 |
| F06. 계정 사용량·비용 보호 | 여러 서버가 계정 한도를 소진하는 문제 완화 | 사용자/Guild 요청량 제한, 조회 TTL 캐시, 실패 backoff; 현재 성공 쿨타임과 분리 | M | 높음 |
| F07. 추가 대화만 이어 요약 | 반복 요약에서 같은 대화를 덜 읽음 | 마지막 성공 종료 경계 이후 원문, 범위/편집/삭제 처리 명시; 이전 요약만 재요약하지 않음 | M~L | 중간 |
| F08. 요약 품질 피드백 | 틀린 화자·숫자·결론을 신고 | 오류 유형·무작위 요청 ID 중심; 원문 복사와 사용자 식별정보 수집 최소화 | M | 중간 |
| F09. 설정 변경 미리보기 | 채널·역할 변경 실수를 줄임 | 추가·제거 diff, 재수집 영향, version 충돌 안내; 저장 전 재권한 검사 유지 | S~M | 중간 |
| F10. 범위 안 답글 연결 | 질문과 대답의 관계를 더 정확히 요약 | 현재 boolean `is_reply`를 범위 안 익명화된 참조로 확장; 다른 채널·범위 밖 자동 수집 금지 | M | 중간 |

F04는 모델이 생성한 URL을 그대로 믿는 기능이 아니다. 수집된 message ID 집합에 포함되는 근거만 코드에서 링크로 만들어야 한다. F05도 설정 백업에 대화 원문을 넣는 기능이 아니며, 삭제 후 자동 백필이 데이터를 되살리지 않도록 상태 정책이 먼저 필요하다.

F07은 단순 결과 캐시보다 어렵다. 범위가 같아도 원문 편집·삭제, 서버 말투, 추가 요청이 다르면 같은 결과를 재사용하면 안 된다. 먼저 B03·B04를 해결하고 재사용 키와 무효화 조건을 정의하는 편이 맞다.

## 제품 경험에 대한 제안

캐릭터 말투와 비평은 유지할 가치가 있다. 다만 서비스 오류·권한 거부·삭제 요청은 핵심 정보가 먼저 보이게 하고, 실제 발언과 봇의 비평은 계속 구분하는 편이 좋다. 형식 변화가 길어지면 휴대폰에서 주제·화자·결정이 빠르게 보이는지 확인해야 한다. 이번 검토는 Discord 화면 실사용 관찰이 아니라 코드·문구·응답 경로 검토다.

상태·도움말은 유효 설정을 반영해야 한다. 예를 들어 `default_minutes`를 바꾸면 현재 고정 “최근 1시간” 도움말과 다를 수 있다(`parser.py:21`, `range_request.py:22–24`). 운영자 설정이 사용자에게 예측 가능한 동작으로 보이게 하는 작은 개선이다.

## 당장 확대하지 않을 범위

| 아이디어 | 보류 이유 |
|---|---|
| 여러 채널·서버의 통합 요약 | 수신자별 권한 교집합과 비공개 대화 재노출 위험이 커짐 |
| 요약을 장기 지식 저장소로 축적 | 삭제·동의·보존기간·검색 권한이라는 별도 제품 정책 필요 |
| 자동 정기 게시 | 잘못된 요약을 반복 공개할 수 있어 opt-in·비용·실패 중복 정책 선행 |
| 첨부·음성·외부 URL 자동 분석 | 입력 범위·민감정보·파일 파서·네트워크 위험이 크게 늘어남 |
| 즉각적인 외부 DB·분산 큐 전환 | 현 규모의 병목 실측 없이 운영 복잡도만 늘 수 있음 |

기능 확대보다 먼저 [버그 문서](02-bug-findings.md)의 권한·동기화·worker 문제를 처리해야 한다. 이후 F01~F06은 새 기능과 운영 안정성을 함께 개선할 수 있는 후보들이다.
