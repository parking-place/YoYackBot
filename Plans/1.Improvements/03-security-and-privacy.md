# 03. 보안과 개인정보 평가

기준: `5f85734`. 정적 코드·합성 검증 중심의 평가이며 침투시험·운영 설정 감사·의존성 CVE 인증이 아니다.

## 총평

요청별 파일·모델 실행 격리와 로그 최소화는 비교적 구체적으로 구현되어 있다. 먼저 고쳐야 할 문제는 **공개 응답의 수신자 권한(B01), 권한 변경의 원자성(B02), 삭제한 원문의 재사용(B03)**이다. 이들은 프롬프트 공격에 성공해야만 생기는 문제가 아니다.

## 자산과 신뢰 경계

| 자산·경계 | 보호해야 할 것 | 현재 통제 | 남은 문제 |
|---|---|---|---|
| Discord 서버·채널 | 다른 서버·비공개 채널의 정보 | Guild/channel 키, 주시 lease, 게시 전 권한 검사 | 목록의 요청자와 공개 수신자 불일치(B01) |
| 봇 관리 역할 | 채널·권한 설정 권한 | 관리자/허용 역할 검사, 소유자 제한, UI revision | 역할 삭제 read-modify-write 경합(B02) |
| 대화 캐시 | 원문·화자·삭제 의도 | 보존 정리, tombstone, private DB, 설정 전용 백업 | 오프라인 삭제·수정(B03), cutoff 불일치(B06) |
| 모델 입력 | 비신뢰 대화·닉네임·추가 요청 | JSONL, 신뢰 경계 프롬프트, 입력 크기 제한 | 의미적 prompt injection·사실 오염은 별도 평가 필요 |

## 확인한 방어 장치

- `input_files.py:62–86`: JSONL로 본문·이름 등을 직렬화한다. 개행·따옴표로 레코드 구조를 임의 삽입하기 어렵다. 이것이 의미적 지시 공격까지 막는 것은 아니다.
- `input_files.py:95–129`: 요청별 0700 디렉터리와 private 임시 파일, 소유자·권한·심볼릭 링크 검사를 사용한다.
- `codex_runner.py:74–78,217–221`: 셸 문자열이 아닌 인자 배열로 subprocess를 실행하고, Discord 인증값을 담은 원래 환경 전체를 전달하지 않는다.
- `codex_runner.py:169–193,206–216`: 요청 입력·인증 사본·출력 및 필요한 런타임 파일을 mount하며 호스트 프로젝트나 Discord 토큰 경로를 통째로 전달하지 않는다.
- `codex.py:91–109`: 모델 도구의 `/auth`·`/output` 접근, 네트워크·웹 탐색 등을 제한하고 호스트 사용자 설정에 의존하지 않도록 한다.
- `codex_runner.py:63–101,228–240,243–295`: 출력 파일의 링크·타입·소유자·크기 확인, timeout/취소 시 프로세스 그룹 종료, 입력 정리, 인증 갱신 CAS가 있다.
- `publisher.py:55–101`: 매 조각의 대상·권한·주시를 확인하고 멘션·embed를 억제한다. 응답 불명확 시 자동 재전송하지 않는다.
- `message_store.py`, `watch_store.py`: 매개변수 SQL, 주시 변경 revision, 삭제 tombstone, 트랜잭션을 사용한다. 동적으로 선택하는 SQL 열 이름은 코드의 고정 선택지이며 사용자 본문을 SQL로 결합하는 경로로 보지 않았다.
- `settings_backup.py`: 관리자 역할을 포함한 설정 전용 백업이다. 원문 백업 누락이 결함인 것이 아니라 의도된 개인정보 최소화다.

이 항목은 코드에 통제가 있다는 확인이다. 현재 운영 호스트에서 그 파일 권한·mount·CLI가 그대로 적용되고 있다는 보증은 아니다.

## 모델 공격과 출력 신뢰

대화·닉네임·추가 요청은 모두 비신뢰 입력이다. 공격적인 문장이 JSON 안에 들어 있다고 모델이 반드시 데이터로만 취급하는 것은 아니다. 프롬프트 분리, 최소 권한, 출력 검증, 공격성 평가를 함께 적용하는 접근이 적절하다. [OWASP LLM01 공식 지침](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

현재 bwrap 구성의 `--share-net`과 모델 도구의 네트워크 금지는 다른 계층이다. 인증된 CLI는 모델 통신이 필요하고, 임의 도구의 연결은 CLI 권한 계층이 제한한다. 따라서 “프로세스 전체가 네트워크 단절되어 있다”거나 “프롬프트만으로 토큰을 읽을 수 있다”고 단정할 수 없다. 실제 canary 읽기·쓰기·외부 연결 검증은 별도 격리 환경에서 수행해야 한다.

`tests/test_request_injection.py`는 직렬화·구분자·프롬프트·고지 처리를 검사한다. 실제 모델의 지시 저항성 통과와 같지 않다. 과거 `docs/security-review-0.8.0.md`의 합성 모델 결과 역시 과거 버전·입력에 대한 증거다. 이번 커밋의 전체 공격면 PASS로 전용하지 않았다.

1.2.0의 서버 말투는 사용자 결정대로 신뢰 프롬프트 안의 하위 규칙으로 들어갈 계획이다. 저장 시 내용 필터를 새로 요구하기보다, 고정 금지선·사실 규칙의 우선순위가 생성 및 평가 후보·심사 경로에서도 유지되는지 검증해야 한다. 후보 심사는 품질 보조 수단이며 권한 검사나 결정적 출력 검사의 대체물이 아니다.

## 개인정보와 권한 정책

**보존과 동기화:** B03·B06을 우선 해소하고, “서버에서 삭제됨”, “캐시에서 제거됨”, “이미 게시된 요약에 남음”을 다른 상태로 설명해야 한다. 이미 생성한 요약을 어떻게 삭제할지는 현재 캐시 TTL만으로 해결되지 않는다. 백업·로그·모델 입력 잔존까지 포함해 실제 수명을 검증할 필요가 있다.

**과거 기록 열람 권한:** 현행 요청 경로는 봇의 `read_message_history`를 검사하지만 요청자의 해당 권한을 검사하지 않는다(`discord.py:540–575`, `workflow.py:61–63`). 현재 채널에 쓸 수 있으나 과거 기록을 못 보는 사용자가 캐시 요약을 요청할 수 있다. 공개 요약이 제품 정책상 허용되는지 먼저 명시해야 한다. 모든 채널 구성에서 확정적인 권한 우회라고 단정하지는 않는다.

**관리 감사:** 변경 이력은 유용하지만 현재 로그가 사용자·채널 ID를 제외하는 정책과 충돌할 수 있다. 추가한다면 공개 journal에 원문·사용자 정보를 넣지 말고, 필요한 식별·열람권한·보존기간을 별도 설정 저장소 정책으로 정의해야 한다.

**자원 사용:** 입력 한도, bounded queue와 모델 동시 실행 제한은 장점이다. B08과 보조 명령의 무제한 대기 때문에 이것만으로 전체 서비스 자원이 제한되는 것은 아니다. systemd 파일에 명시적 MemoryMax·TasksMax 등은 없다. 실제 부하를 측정한 뒤 bwrap와 인증 갱신에 호환되는 자원·파일시스템 제한을 검토해야 한다. 무작정 hardening 옵션을 켜서 서비스를 깨뜨리지 않는다.

## 공급망과 비밀정보 검사

| 검사·구성 | 이번 확인 | 해석 |
|---|---|---|
| `requirements.lock` | 17개 버전 고정, 사용한 검증 venv와 모두 일치 | 버전 재현성 확인; 배포물 해시 고정은 아님 |

| 운영 Codex·bwrap 바이너리 검증 | 미실행 | 바이너리 출처·checksum·실행 설정은 별도 확인 필요 |

Actions를 full commit SHA로 고정하고 갱신 이력을 관리하면 이동 가능한 태그의 위험을 줄일 수 있다. 이는 GitHub의 공식 권고와도 일치한다. [GitHub Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions).

정기 advisory 검사는 고정 의존성의 취약점 변화를 다루는 별도 절차로 두는 것이 좋다. 이번 보고서에서는 검증되지 않은 CVE나 패키지 위험 등급을 만들어 넣지 않았다.
