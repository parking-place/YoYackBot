## Discord 채널 요약 봇 기능 명세서

- 문서 유형: 기능 / 동작 명세서
- 구현 대상: Discord Bot
- 실행 환경: Linux LXC
- 요약 엔진: Codex CLI
- 사용 모델: GPT-6 Luna Light
- 기본 시간대: Asia/Seoul
- 구현 코드: 본 문서에 포함하지 않음

---

# 1. 개요

**신창섭이 요약을 정상화하네**는 Discord 채널의 최근 대화를 수집하여 Codex CLI로 요약한 뒤, 해당 채널에 다시 게시하는 전용 요약 봇이다.

사용자가 채팅에 `!!요약좀`이라는 문자열을 포함한 메시지를 작성하면 봇이 이를 인식하고, 명령 옵션에 따라 해당 채널의 과거 메시지를 수집한다.

수집된 로그는 임시 파일로 저장하며, Codex CLI는 해당 임시 파일을 입력 자료로 사용해 내용을 요약한다.

요약 결과는 단순한 주제 정리뿐만 아니라 **누가 어떤 이야기를 했는지 화자 중심으로 파악할 수 있도록 작성**해야 한다.

봇이 사용자에게 출력하는 안내 문구와 요약문 전체의 기본 말투는 **고풍스러운 `-하오체`**를 사용한다.

---

# 2. 핵심 목표

본 봇의 핵심 목표는 다음과 같다.

1. Discord 특정 채널의 최근 대화를 명령 한 번으로 요약한다.
2. 사용자가 원하는 시간 또는 메시지 개수만큼 수집 범위를 지정할 수 있다.
3. 요약 대상에서 모든 봇 메시지를 제외한다.
4. 로그 수집 결과를 임시 파일로 저장한다.
5. Codex CLI가 임시 파일을 읽어 요약하도록 한다.
6. 요약 결과에서 주요 참여자와 각 참여자의 발언 내용을 구분한다.
7. 봇의 전체 출력 문체를 자연스러운 고풍스러운 `-하오체`로 유지한다.
8. 연속 호출을 방지하기 위해 처리 중 및 성공 후 쿨타임을 적용한다.
9. 최근 Discord 메시지를 SQLite에 최대 7일간 캐시하여 반복 조회를 줄인다.
10. 이전 요약 범위와 겹치는 요청은 SQLite 캐시를 재사용하고, 누락된 구간만 Discord에서 추가 조회한다.
11. Discord 서버별로 `/채널 설정`을 통해 요약봇이 주시할 채널을 선택할 수 있다.
12. 주시 대상으로 설정된 채널의 일반 사용자 메시지만 SQLite에 실시간 캐시한다.

# 4. 전체 동작 흐름

전체 처리 흐름은 다음과 같다.

1. Discord 메시지 수신
2. 메시지가 주시 대상 채널에서 발생했는지 확인
3. 주시 대상 채널의 일반 사용자 메시지라면 SQLite 메시지 캐시에 저장
4. 메시지에 `!!요약좀 도움` 또는 `!!요약좀`이 포함되어 있는지 확인
5. 명령 및 옵션 해석
6. 현재 채널이 주시 대상인지 확인
7. 현재 채널의 쿨타임 상태 확인
8. 요약 요청 범위 계산
9. SQLite 캐시에 필요한 메시지가 존재하는지 확인
10. 캐시에 없는 시간 구간 또는 메시지가 있으면 Discord History에서 누락분만 추가 수집
11. 수집 과정에서 봇 계정 및 자동화 메시지 제거
12. 신규 수집 메시지를 SQLite에 중복 없이 저장
13. 요청 범위에 해당하는 메시지를 SQLite에서 조회
14. 현재 `!!요약좀` 명령 메시지를 요약 대상에서 제외
15. 메시지를 오래된 순서대로 정리
16. Codex 입력용 임시 로그 파일 생성
17. Codex CLI에 임시 로그 파일을 요약하도록 요청
18. Codex CLI의 최종 요약 결과 수신
19. 요약 성공 여부 판정
20. 성공 시 5분 성공 쿨타임 적용
21. Discord 채널에 요약 결과 게시
22. Codex 입력용 임시 파일 삭제
23. 7일이 지난 SQLite 캐시 레코드 정리

개념 흐름은 다음과 같다.

```text
Discord 채널
    ↓
일반 사용자 메시지 수신
    ↓
SQLite 7일 캐시
    ↓
명령 감지
    ↓
옵션 해석
    ↓
쿨타임 확인
    ↓
요약 범위 계산
    ↓
SQLite 캐시 조회
    ├─ 필요한 범위가 캐시에 있음 → 재사용
    └─ 누락 구간 존재 → Discord History에서 누락분만 조회
                               ↓
                           SQLite에 저장
    ↓
요청 범위 메시지 SELECT
    ↓
Codex 입력용 임시 로그 파일 생성
    ↓
Codex CLI
    ↓
GPT-6 Luna Light 요약
    ↓
결과 수신
    ↓
Discord 채널 게시
    ↓
임시 파일 삭제
```

# 4-1. 주시 채널 설정

봇은 Discord 서버의 모든 채널을 자동으로 수집하지 않는다.

서버별로 `/채널 설정`을 통해 **요약봇이 주시할 채널을 명시적으로 선택**한다.

주시 대상으로 등록된 채널에서만 다음 기능을 수행한다.

- 일반 사용자 메시지 실시간 감지
- SQLite 메시지 캐시 저장
- `!!요약좀` 명령 실행
- Discord History 보충 조회
- 요약 결과 게시

주시 대상이 아닌 채널의 일반 대화는 SQLite에 저장하지 않는다.

---

# 4-2. `/채널 설정`

## 명령

```text
/채널 설정
```

Discord Slash Command 형태로 제공한다.

명령을 실행하면 현재 서버에서 봇이 접근 가능한 텍스트 채널 중 **주시할 채널을 선택할 수 있는 UI**를 제공한다.

구현상 가능한 경우 Discord Channel Select UI를 사용하며, 복수 채널 선택을 지원하는 것을 권장한다.

설정 예:

```text
주시 채널

☑ #잡담
☑ #개발
☐ #봇-명령어
☐ #공지
```

사용자가 설정을 저장하면 선택된 채널 목록을 해당 Discord 서버의 주시 채널 설정으로 저장한다.

---

# 4-3. 주시 채널 설정 단위

주시 채널 설정은 **Discord 서버(Guild) 단위**로 관리한다.

예:

```text
서버 A
- #잡담
- #개발

서버 B
- #일반
```

서버 A의 설정은 서버 B에 영향을 주지 않는다.

각 서버는 독립적인 주시 채널 목록을 가진다.

---

# 4-4. `/채널 설정` 권한

`/채널 설정`은 일반 사용자가 임의로 변경하지 못하도록 제한하는 것을 권장한다.

기본 권장 권한:

- 서버 관리자
- `Manage Channels` 권한 보유자
- 또는 별도로 지정한 봇 관리자 역할

권한이 없는 사용자가 실행한 경우 설정을 변경하지 않는다.

권장 안내 문구:

```text
이 설정은 관리할 권한이 있는 자만 바꿀 수 있소.
```

정확한 권한 정책은 운영 환경에 맞게 설정 가능하도록 한다.

---

# 4-5. 주시 채널 설정 저장

주시 채널 목록은 봇 재시작 후에도 유지되어야 한다.

따라서 설정값을 영속 저장한다.

SQLite를 사용하는 경우 메시지 캐시 DB와 동일 DB 내부의 별도 설정 테이블을 사용할 수 있다.

권장 논리 구조:

| 필드 | 설명 |
|---|---|
| `guild_id` | Discord 서버 ID |
| `channel_id` | 주시 대상 채널 ID |
| `enabled` | 주시 활성 여부 |
| `updated_at` | 마지막 설정 변경 시각 |

`guild_id + channel_id` 조합은 중복되지 않도록 관리한다.

---

# 4-6. 주시 채널 추가 시 동작

새로운 채널을 주시 대상으로 추가하면 **설정 이후부터 수신되는 일반 사용자 메시지를 실시간 캐시**한다.

단, 이후 사용자가 해당 채널에서 `!!요약좀`을 실행하고 요청 범위에 과거 메시지가 필요한 경우 SQLite에 없는 구간은 Discord History에서 보충 조회할 수 있다.

예:

```text
18:00 #개발 채널을 주시 대상으로 추가
18:10 !!요약좀 2시간
```

이 경우 SQLite에는 18:00 이후 메시지만 있을 수 있으므로:

```text
16:10 ~ 18:00
```

구간은 Discord History에서 추가 조회하고 캐시에 저장한다.

---

# 4-7. 주시 채널 제거 시 동작

주시 대상에서 제거된 채널은 즉시 실시간 메시지 캐시 대상에서 제외한다.

이후 해당 채널에서 발생하는 새 메시지는 SQLite에 저장하지 않는다.

기존 SQLite 캐시에 남아 있는 해당 채널 메시지는 즉시 삭제하지 않아도 되며, 기본 7일 보존 정책에 따라 자연스럽게 제거할 수 있다.

운영자가 원할 경우 주시 해제 시 해당 채널 캐시를 즉시 삭제하는 옵션을 향후 추가할 수 있다.

---

# 4-8. 주시하지 않는 채널에서 `!!요약좀`

주시 대상이 아닌 채널에서는 요약을 실행하지 않는다.

사용자가 `!!요약좀`을 입력한 경우 권장 응답:

```text
이 채널은 아직 살피고 있지 않소. `/채널 설정`으로 먼저 정하시오.
```

이 경우:

- Codex CLI를 실행하지 않는다.
- Discord History를 조회하지 않는다.
- 성공 후 5분 쿨타임을 발생시키지 않는다.
- 해당 채널 메시지를 SQLite에 새로 저장하지 않는다.

# 5. 명령어

# 5.1 도움말

## 명령

`!!요약좀 도움`

## 동작

사용자에게 `!!요약좀`의 사용 방법과 옵션을 보기 좋은 형태로 안내한다.

`!!요약좀 도움` 명령 자체는 요약 기능을 실행하지 않는다.

## 도움말 출력 예시

```text
📜 요약 사용법을 알려드리겠소.

`!!요약좀`
최근 1시간의 대화를 요약하오.

`!!요약좀 3`
최근 3시간의 대화를 요약하오.

`!!요약좀 30분`
최근 30분의 대화를 요약하오.

`!!요약좀 2시간`
최근 2시간의 대화를 요약하오.

`!!요약좀 100개`
최근 일반 사용자 메시지 100개를 요약하오.

`!!요약좀 오늘`
오늘 00시 00분부터 지금까지의 대화를 요약하오.

`!!요약좀 2일`
최근 2일간의 대화를 요약하오.

`!!요약좀 1주`
최근 1주간의 대화를 요약하오.

숫자만 적으면 시간 단위로 알아듣겠소.
```

도움말의 문구와 장식은 구현 시 조금 조정할 수 있으나, 전체 말투는 `-하오체`를 유지한다.

# 5.2 기본 요약 명령

## 명령

`!!요약좀`

## 동작

명령이 작성된 현재 Discord 채널의 **최근 1시간** 대화를 수집하여 요약한다.

## 예시

```text
!!요약좀
```

수집 범위:

```text
현재 시각 - 1시간
~
현재 시각
```

# 5.6 메시지 개수 단위

## 명령 형식

```text
!!요약좀 X개
```

## 예시

```text
!!요약좀 100개
```

현재 채널에서 가장 최근의 **요약 대상 메시지 100개**를 수집한다.

메시지 개수 계산 시 다음 항목은 개수에 포함하지 않는다.

- 요약봇 자신의 메시지
- 다른 Discord 봇의 메시지
- 웹훅 등 명백한 자동화 계정의 메시지
- 이번 요약을 실행한 `!!요약좀` 명령 메시지

따라서 `100개`는 가능한 한 **실제 일반 사용자의 대화 메시지 100개**를 의미한다.

# 6. 명령 인식 규칙

`!!요약좀`은 메시지 전체가 정확히 명령과 일치할 필요는 없다.

메시지 안에 `!!요약좀` 문자열이 들어 있으면 명령 후보로 인식한다.

예:

```text
!!요약좀
```

```text
신창섭아 !!요약좀
```

```text
지금까지 대화 !!요약좀 3시간
```

모두 인식할 수 있다.

다만 옵션 해석은 `!!요약좀` 문자열 이후의 내용을 우선 사용한다.

예:

```text
신창섭아 !!요약좀 30분 부탁하오
```

위 메시지에서는 `30분`을 요약 범위로 해석할 수 있다.

명령 해석이 애매하거나 지원하지 않는 옵션이 포함된 경우 임의로 과도하게 추측하지 않고 사용법을 안내한다.

---

# 7. 옵션 해석 우선순위

`!!요약좀` 이후 옵션은 다음 우선순위로 해석한다.

1. `오늘`
2. `X개`
3. `X분`
4. `X시간`
5. `X일`
6. `X주`
7. 단위 없는 숫자 `X`
8. 옵션 없음

단위 없는 숫자는 항상 **시간**으로 처리한다.

예:

```text
!!요약좀 5
```

→ 최근 5시간

```text
!!요약좀 5분
```

→ 최근 5분

```text
!!요약좀 5개
```

→ 최근 일반 사용자 메시지 5개

---

# 8. 로그 수집 범위

요약 명령은 **명령을 호출한 현재 Discord 채널만** 대상으로 한다.

단, 해당 채널은 `/채널 설정`을 통해 주시 대상으로 등록되어 있어야 한다.

다른 채널의 메시지는 수집하지 않는다.

예:

```text
#잡담 채널에서 !!요약좀
```

을 실행하면 `#잡담` 채널만 수집한다.

다음 채널의 메시지는 자동으로 합치지 않는다.

- 다른 텍스트 채널
- 스레드
- 포럼의 다른 게시물
- 음성 채널 텍스트
- 다른 Discord 서버

향후 기능 확장을 하지 않는 이상, 기본 원칙은 **현재 명령이 실행된 채널 하나만 요약**하는 것이다.

---

# 9. 로그 수집 제외 대상

다음 메시지는 요약 입력 로그에서 반드시 제외한다.

## 9.1 요약봇 자신의 메시지

**신창섭이 요약을 정상화하네**가 작성한 모든 메시지는 제외한다.

예:

```text
요약중이오.
아직은 때가 아니오.
XX부터 지금까지의 요약이오.
```

등은 다음 요약에서 다시 입력으로 사용하지 않는다.

---

## 9.2 다른 봇의 메시지

Discord API상 Bot 계정으로 판단되는 모든 메시지는 제외한다.

예:

- 음악 봇
- 관리 봇
- 알림 봇
- 게임 봇
- 기타 자동화 봇

원칙:

```text
Human User Message → 포함
Bot Message → 제외
```

---

## 9.3 웹훅 / 자동화 메시지

가능한 경우 Discord 웹훅 또는 자동화 시스템에서 작성된 메시지도 제외하는 것을 기본 정책으로 한다.

---

## 9.4 현재 요약 명령 메시지

현재 요약을 실행하기 위해 사용자가 작성한 메시지도 요약 대상에서 제외한다.

예:

```text
!!요약좀 3시간
```

이 문자열 자체가 요약 내용에 포함되지 않아야 한다.

# 10. 수집 로그 형식

수집한 메시지는 Codex가 화자와 시간 순서를 명확히 이해할 수 있는 구조로 정리한다.

권장 논리 구조:

[메시지 작성 시각] 사용자 표시명

```

또는 이에 준하는 명확한 구조를 사용한다.

- 메시지 본문
- 시간 순서

- 첨부파일 존재 여부
- URL
- 답장 대상 사용자
- 메시지 ID

다만 기본 요약 목적상 불필요한 Discord 내부 메타데이터는 최소화한다.

...

14:22 민수
...
```

이 순서를 유지해야 대화 흐름을 정확하게 요약할 수 있다.

# 12. 임시 파일

수집이 완료되면 Discord 로그를 임시 파일로 저장한다.

## 목적

- 긴 Discord 로그를 CLI 명령 인자로 직접 넘기는 문제 방지
- 특수문자 및 따옴표 처리 문제 방지
- 긴 대화 처리 용이
- Codex CLI가 원문 파일을 직접 참고할 수 있도록 구성

## 임시 파일에는 다음 내용만 포함한다.

- 요약 범위 정보
- 채널 정보
- 수집된 일반 사용자 메시지
- 각 메시지 작성자
- 작성 시각
- 메시지 본문

Discord Bot Token, Codex 인증 정보 등 민감한 정보는 포함하지 않는다.

---

# 13. 임시 파일 생명주기

임시 파일은 **SQLite 메시지 캐시와 별개의 Codex 입력 전용 파일**이다.

SQLite에는 최근 7일간의 메시지를 보관하지만, Codex 입력용 임시 파일은 매 요청마다 필요한 범위만 추출하여 생성한다.

기본 흐름:

```text
SQLite 메시지 캐시
↓
이번 요청 범위 SELECT
↓
Codex 입력용 임시 파일 생성
↓
Codex CLI 실행
↓
요약 결과 수신
↓
임시 파일 삭제
```

Codex 입력용 임시 파일은 장기 캐시로 사용하지 않는다.

요약 성공 또는 실패 여부와 관계없이 작업이 끝나면 삭제하는 것을 원칙으로 한다.

다음 상황에서도 가능한 한 임시 파일을 정리해야 한다.

- Codex CLI 오류
- 요약 제한 시간 초과
- Discord 전송 실패
- 예외 발생
- 프로세스 종료

봇이 비정상 종료되어 임시 파일이 남을 가능성에 대비해 시작 시 오래된 임시 파일을 정리하는 보조 정책을 둘 수 있다.

장기 보존 및 기간 중복 재사용은 임시 파일이 아니라 **SQLite 메시지 캐시**가 담당한다.

---

# 13-1. SQLite 메시지 캐시 개요

최근 Discord 대화를 반복해서 History API로 다시 가져오는 것을 줄이기 위해 SQLite 기반 메시지 캐시를 운영한다.

SQLite의 역할은 다음과 같다.

- 최근 일반 사용자 메시지 저장
- 최대 7일간 rolling cache 유지
- 동일 메시지 중복 저장 방지
- 시간 범위 기반 조회
- 최근 메시지 개수 기반 조회
- 서로 겹치는 요약 요청에서 기존 데이터 재사용
- 캐시에 없는 구간만 Discord에서 보충 조회

SQLite는 영구 보관용 채팅 아카이브가 아니라 **요약 작업 최적화를 위한 단기 캐시**로 취급한다.

---

# 13-2. SQLite 캐시 보존 기간

메시지 캐시의 기본 보존 기간은 다음과 같다.

**7일**

기준:

```text
현재 시각 - 7일
```

보다 오래된 메시지는 자동 삭제 대상이다.

삭제 기준은 메시지 생성 시각 `created_at`을 기본으로 한다.

권장 정리 시점:

- 봇 시작 시
- 일정 주기마다
- 요약 작업 종료 후 선택적으로
- 캐시 크기가 설정된 기준을 초과한 경우

7일이 지난 메시지는 요약 캐시에서 제거하며, 장기적인 대화 기록 보관 목적으로 유지하지 않는다.

---

# 13-3. 권장 SQLite 메시지 구조

메시지 캐시에는 최소한 다음 정보를 저장한다.

| 필드 | 설명 |
|---|---|
| `message_id` | Discord Message ID, 기본 키 |
| `guild_id` | Discord 서버 ID |
| `channel_id` | Discord 채널 ID |
| `author_id` | 작성자 Discord User ID |
| `author_name` | 수집 당시 표시명 |
| `content` | 메시지 본문 |
| `created_at` | Discord 메시지 작성 시각 |
| `edited_at` | 수정 시각, 존재하는 경우 |
| `cached_at` | SQLite에 저장된 시각 |

`message_id`를 기본 키 또는 고유 키로 사용하여 동일한 Discord 메시지가 여러 번 조회되더라도 중복 저장되지 않도록 한다.

봇 메시지는 기본적으로 DB에 저장하지 않는다.

---

# 13-4. 캐시 저장 정책

기본 권장 방식은 **주시 채널 한정 실시간 7일 rolling cache**이다.

일반 사용자가 메시지를 작성하면 다음 조건을 확인한 뒤 SQLite에 저장한다.

```text
메시지 수신
↓
주시 대상 채널인가?
    ├─ NO  → 저장하지 않음
    └─ YES
        ↓
    일반 사용자 메시지인가?
        ├─ YES → SQLite 저장
        └─ NO  → 저장하지 않음
```

다음 메시지는 캐시에 저장하지 않는 것을 기본값으로 한다.

- `신창섭이 요약을 정상화하네` 자신의 메시지
- 기타 Discord Bot 메시지
- 웹훅 및 자동화 메시지
- 시스템성 메시지

`!!요약좀` 명령을 작성한 사용자는 일반 사용자이므로 해당 메시지가 SQLite에 들어갈 수 있으나, **해당 요약 작업의 입력을 생성할 때는 현재 명령 메시지를 반드시 제외**한다.

과거에 저장된 다른 요약 명령 메시지 역시 실제 대화 의미가 없다고 판단되는 경우 입력 생성 단계에서 제외하도록 구성할 수 있다.

---

# 13-5. 기간 중복 재사용

요약 요청 기간이 이전 요청과 일부 또는 전체 겹치는 경우 SQLite에 이미 저장된 메시지를 우선 재사용한다.

예:

```text
18:00
!!요약좀 1시간
```

필요 범위:

```text
17:00 ~ 18:00
```

이후:

```text
18:20
!!요약좀 2시간
```

필요 범위:

```text
16:20 ~ 18:20
```

SQLite에 이미 `17:00 ~ 18:00` 구간 메시지가 저장되어 있다면 해당 구간은 다시 Discord에서 가져오지 않는다.

누락 구간만 추가 조회한다.

```text
16:20 ~ 17:00  → Discord에서 보충 조회
17:00 ~ 18:00  → SQLite 캐시 재사용
18:00 ~ 18:20  → Discord에서 보충 조회
```

보충 조회 결과는 다시 SQLite에 저장한다.

최종 요약 입력은 SQLite에서 전체 요청 범위를 다시 조회하여 생성한다.

---

# 13-6. 캐시 범위 메타데이터

단순히 DB에 메시지가 존재한다는 이유만으로 해당 시간 범위가 완전히 캐시되었다고 판단해서는 안 된다.

예를 들어 `17:00`과 `18:00` 사이에 메시지가 몇 개 존재하더라도, 중간 구간을 실제로 Discord에서 조회한 적이 없다면 누락 여부를 알 수 없다.

따라서 채널별로 **수집 완료 범위 메타데이터**를 관리하는 것을 권장한다.

개념 예:

| 필드 | 설명 |
|---|---|
| `channel_id` | 채널 ID |
| `range_start` | Discord History 수집이 완료된 시작 시각 |
| `range_end` | Discord History 수집이 완료된 종료 시각 |
| `updated_at` | 범위 갱신 시각 |

서로 인접하거나 겹치는 수집 범위는 병합할 수 있다.

예:

```text
16:00 ~ 17:00
16:50 ~ 18:00
```

은 다음처럼 병합한다.

```text
16:00 ~ 18:00
```

이 메타데이터를 통해 실제 메시지 수와 무관하게 어느 시간 구간을 완전히 조회했는지 판단한다.

---

# 13-7. 캐시 누락 구간 계산

시간 범위 기반 요약 요청에서는 다음 순서로 동작한다.

1. 요청 시작 시각과 종료 시각 계산
2. 채널의 캐시 수집 완료 범위 조회
3. 요청 범위와 겹치는 캐시 범위 계산
4. 아직 수집되지 않은 구간 계산
5. 누락 구간만 Discord History API에서 조회
6. 신규 메시지를 SQLite에 저장
7. 수집 완료 범위 메타데이터 갱신
8. 전체 요청 범위를 SQLite에서 조회
9. Codex 입력용 임시 파일 생성

목표는 같은 Discord 메시지를 반복적으로 History API에서 조회하는 일을 최소화하는 것이다.

---

# 13-8. `X개` 옵션과 SQLite 캐시

`!!요약좀 X개`는 시간 범위가 아니라 **가장 최근 일반 사용자 메시지 개수**가 기준이다.

우선 SQLite에서 현재 채널의 최근 메시지를 조회한다.

```text
최신순 조회
→ 일반 사용자 메시지만
→ X개
```

SQLite에 X개 이상 존재하면 Discord History API를 다시 호출하지 않는다.

SQLite에 필요한 개수보다 적은 메시지만 존재하는 경우 이전 시점의 Discord History를 추가 조회하여 부족한 개수를 채운다.

추가로 수집된 메시지는 SQLite에 저장한다.

최종적으로 가장 최근 일반 사용자 메시지 X개를 시간순으로 다시 정렬하여 Codex에 전달한다.

---

# 13-9. `오늘` 옵션과 SQLite 캐시

`!!요약좀 오늘`은 `Asia/Seoul` 기준 오늘 00:00부터 현재까지가 대상이다.

예:

```text
2026-09-28 00:00 KST
~
2026-09-28 18:30 KST
```

SQLite 캐시 범위가 해당 구간을 모두 포함한다면 DB 데이터만 사용한다.

일부 구간이 없다면 해당 부분만 Discord에서 추가로 조회한다.

---

# 13-10. 수정 및 삭제된 Discord 메시지

메시지 수정 이벤트를 받을 수 있는 경우 SQLite의 기존 레코드를 갱신하는 것을 권장한다.

삭제 이벤트를 받을 수 있는 경우 해당 메시지를 SQLite에서도 제거하는 것을 권장한다.

단, 봇이 오프라인인 동안 발생한 수정 또는 삭제는 완전히 추적하지 못할 수 있다.

History API를 통해 동일한 메시지를 다시 조회한 경우 최신 내용을 기준으로 캐시 레코드를 갱신할 수 있다.

SQLite 캐시는 Discord의 절대적인 감사 로그가 아니라 **요약 편의를 위한 단기 캐시**임을 전제로 한다.

---

# 13-11. SQLite 인덱스 권장사항

구현 시 다음 조회가 빈번하게 발생한다.

- 채널 + 시간 범위 조회
- 채널 + 최신 메시지 조회
- 7일이 지난 메시지 삭제

따라서 다음 조합에 적절한 인덱스를 두는 것을 권장한다.

```text
channel_id + created_at
created_at
```

`message_id`는 고유 키로 관리한다.

---

# 13-12. SQLite 파일 관리

SQLite 데이터베이스 파일은 LXC 내부의 영속 저장 경로에 둔다.

임시 디렉터리에 두지 않는다.

예시 개념:

```text
/var/lib/<bot-name>/messages.db
```

정확한 경로는 구현 설정값으로 분리한다.

SQLite DB에는 Discord Bot Token, Codex 인증 토큰, 비밀번호 등의 인증 정보를 저장하지 않는다.

---

# 13-13. 캐시 장애 시 동작

SQLite 조회 또는 저장에 문제가 발생하더라도 Discord 원본 대화가 손실된 것은 아니다.

가능한 경우 다음과 같이 graceful fallback을 적용한다.

```text
SQLite 캐시 사용 실패
↓
Discord History에서 요청 범위 직접 조회
↓
Codex 입력 파일 생성
↓
요약 수행
```

다만 DB 오류가 심각하거나 데이터 무결성이 의심되는 경우 사용자에게 요약 실패를 안내하고 작업을 종료할 수 있다.

캐시는 최적화 계층이며, 가능한 한 요약 기능 자체와 느슨하게 결합한다.

요약 모델은 다음을 사용한다.

**GPT-6 Luna Light**

Codex에게는 일반적인 코딩 에이전트 업무가 아닌 **Discord 대화 요약 작업**임을 명확히 전달한다.

Codex가 다른 시스템 파일이나 프로젝트 파일을 탐색할 필요는 없다.

# 16. 화자 중심 요약

```text
서버 이전과 네트워크 변경에 대해 이야기했소.
```

라고만 작성하는 것을 피한다.

가능한 경우 다음과 같이 작성한다.

```text
쭈는 서버 이전 일정을 다음 주로 잡자고 제안하였소.

철수는 현재 백업 용량이 부족하므로 먼저 스토리지를 정리해야 한다고 하였소.

```

다만 모든 짧은 잡담을 사용자별로 나열할 필요는 없다.

중요한 논의, 주장, 질문, 합의, 결정 사항을 중심으로 화자를 명시한다.

# 19. 요약 결과 권장 구조

📜 주요 이야기

- B는 이에 대해 어떤 의견을 냈소.

- 어떤 부분은 결론이 나지 않았소.
```

대화 내용상 해당 항목이 없다면 억지로 빈 섹션을 만들 필요는 없다.

✅ 정해진 것

요약 봇은 Codex CLI를 사용하기로 하였소.
```

# 21. 범위 표시 규칙

요약 결과 첫 문장의 `XX`는 실제 요약 시작 시점을 표시한다.

## 최근 1시간

```text
오후 4시 30분부터 지금까지의 요약이오.
```

## 오늘

```text
오늘 00시 00분부터 지금까지의 요약이오.
```

## 2일

필요한 경우 날짜까지 표시한다.

```text
9월 26일 오후 5시 30분부터 지금까지의 요약이오.
```

## 메시지 개수 기준

`X개` 옵션은 정확한 시간 범위보다 메시지 개수가 기준이므로, 수집된 가장 오래된 메시지의 시각을 사용한다.

예:

```text
오후 1시 12분부터 지금까지의 요약이오.
```

# 22. Discord 메시지 길이 처리

Discord 메시지 최대 길이를 초과할 정도로 요약이 길어진 경우 여러 메시지로 나누어 전송한다.

분할 시 다음 원칙을 지킨다.

1. 문장 중간을 가급적 자르지 않는다.
2. Markdown 구조를 가능한 유지한다.
3. 여러 메시지의 순서가 명확해야 한다.
4. 첫 메시지에만 다음 문구를 표시한다.

```text
XX부터 지금까지의 요약이오.
```

두 번째 이후 메시지는 요약 본문만 이어서 전송할 수 있다.

# 23. 쿨타임 개요

`!!요약좀`은 연속 실행을 방지하기 위해 두 종류의 상태를 가진다.

1. **요약 처리 중 상태**
2. **요약 성공 후 5분 쿨타임**

기존의 별도 `1분 인식 쿨타임` 개념은 사용하지 않는다.

새 요청이 들어왔을 때 현재 요약 작업이 실제로 진행 중이면 새 작업을 시작하지 않고 처리 중 안내만 출력한다.

---

# 24. 요약 처리 중 상태

사용 가능한 요약 명령을 정상적으로 인식하여 요약 처리를 시작하면 즉시 처리 중 상태가 된다.

처리 중에는 새로운 `!!요약좀` 요청을 받더라도 새 요약 작업을 동시에 실행하지 않는다.

처리 중 다시 명령이 들어오면 다음 문구로 응답한다.

```text
요약중이오. 좀 기다리시오.
```

처리 중 상태에는 별도의 고정 시간 제한이나 남은 시간 카운트다운을 표시하지 않는다.

현재 요약 작업이 끝날 때까지 동일 채널의 새로운 요약 요청은 실행하지 않는다.

---

# 25. 요약 성공 후 쿨타임

요약이 정상적으로 완료되고 Discord에 결과 게시까지 성공하면 다음 쿨타임을 적용한다.

**5분**

이 기간 동안 새로운 `!!요약좀` 명령이 들어오면 새 요약을 시작하지 않는다.

응답:

```text
아직은 때가 아니오. 00분 00초 뒤에 오시오.
```

예:

```text
아직은 때가 아니오. 03분 17초 뒤에 오시오.
```

---

# 26. 쿨타임 우선순위

상태 확인 우선순위는 다음과 같다.

```text
현재 요약 작업 진행 중인가?
    ↓ YES
"요약중이오."
    ↓ NO
성공 후 5분 쿨타임인가?
    ↓ YES
"아직은 때가 아니오."
    ↓ NO
새 요약 시작
```

처리 중 상태가 성공 후 쿨타임보다 우선한다.

---

# 27. 쿨타임 기준 단위

기본적으로 쿨타임은 **채널 단위**로 관리하는 것을 권장한다.

예:

```text
#잡담 → 요약 진행 중
#서버 → 사용 가능
```

이 경우 `#잡담`에서 요약 중이더라도 `#서버`에서는 별도 요약을 실행할 수 있다.

단, Codex CLI 동시 실행을 제한하려는 경우 전역 작업 큐를 별도로 둘 수 있다.

본 명세에서 사용자에게 보이는 쿨타임의 논리 기준은 채널 단위이다.

---

# 28. Codex 요약이 오래 걸리는 경우

요약 처리 중에는 경과 시간과 관계없이 동일 채널에서 두 번째 요약을 동시에 시작하지 않는다.

즉:

```text
요약 작업 실행 중
→ 항상 새로운 요약 금지
```

가 기본 원칙이다.

Codex 요약이 오래 걸리더라도 사용자에게 임의의 예상 남은 시간을 표시하지 않는다.

처리 중 재호출에는 항상 다음 문구를 사용한다.

```text
요약중이오. 좀 기다리시오.
```

동일 채널에서 병렬 요약은 허용하지 않는다.

---

# 29. 요약 실패 시 쿨타임

Codex CLI 오류, 임시 파일 오류, Discord 조회 실패 등으로 요약이 정상 완료되지 못한 경우 **성공 후 5분 쿨타임은 적용하지 않는다.**

실패한 작업은 종료 처리하며 해당 채널은 다시 요약을 요청할 수 있는 상태로 복귀한다.

단, 오류가 너무 빠르게 반복되는 것을 방지하기 위한 짧은 내부 오류 제한은 구현 시 별도로 둘 수 있다.

---

# 30. 오류 메시지 말투

오류 안내 역시 하오체를 유지한다.

예:

```text
대화를 불러오지 못하였소. 잠시 뒤 다시 시도하시오.
```

```text
요약에 실패하였소. 잠시 뒤 다시 명하시오.
```

```text
요약할 만한 대화가 없소.
```

```text
명령을 알아듣지 못하였소. `!!요약좀 도움`을 살펴보시오.
```

내부 예외 정보, 파일 경로, 토큰, 인증 정보, 스택 트레이스 등은 Discord 사용자에게 노출하지 않는다.

---

# 31. 요약할 메시지가 없는 경우

옵션에 해당하는 범위 안에 일반 사용자 메시지가 하나도 없다면 Codex CLI를 실행하지 않아도 된다.

응답 예:

```text
요약할 만한 대화가 없소.
```

이 경우 성공 후 5분 쿨타임 적용 여부는 구현 정책으로 선택할 수 있으나, 기본 권장값은 **적용하지 않음**이다.

---

# 32. 잘못된 옵션

지원하지 않는 옵션을 사용한 경우 요약을 실행하지 않는다.

예:

```text
!!요약좀 많이
```

```text
!!요약좀 어제쯤
```

응답 예:

```text
그 명은 알아듣기 어렵소. `!!요약좀 도움`에서 사용법을 살펴보시오.
```

# 33. 숫자 검증

다음 값은 정상 옵션으로 취급하지 않는다.

- 0
- 음수
- 숫자로 해석할 수 없는 값
- 비정상적으로 큰 값
- 범위를 벗어난 값

예:

```text
!!요약좀 0시간
```

은 거부한다.

# 34. 권장 최대 수집 범위

서버 부하, Discord 조회량, Codex 컨텍스트 크기 등을 고려하여 최대 범위를 설정 가능하게 한다.

향후 실제 사용량에 따라 조정할 수 있다.

# 35. 첨부파일

첨부파일 자체의 바이너리 내용을 다운로드하여 요약하는 기능은 기본 범위에서 제외한다.

다만 메시지에 첨부파일이 있다면 다음과 같이 존재 사실 정도는 기록할 수 있다.

```text
[첨부파일: example.png]
```

Codex가 이미지, 영상, 압축파일 내용을 자동으로 분석하는 것은 본 봇의 기본 기능에 포함하지 않는다.

# 36. 링크

메시지 본문에 포함된 URL은 일반 텍스트의 일부로 수집할 수 있다.

Codex가 외부 링크를 직접 방문하거나 추가 조사하도록 요구하지 않는다.

요약은 **수집된 Discord 대화 내용만**을 근거로 한다.

# 37. 멘션

Discord 사용자 멘션은 가능하면 사람이 읽을 수 있는 표시명으로 정규화한다.

예:

```text
<@123456789>
```

보다는

```text
@철수
```

형태가 요약 입력에 적합하다.

채널 멘션, 역할 멘션 역시 가능한 경우 읽기 쉬운 형태로 변환한다.

사용자명이 변경되더라도 해당 로그 수집 시점의 사람이 알아보기 쉬운 이름을 Codex에 전달하는 것을 우선한다.

공용 `/tmp` 영역을 사용하더라도 파일 이름 충돌이나 다른 사용자 접근을 방지할 수 있는 방식으로 생성한다.

# 41. Codex 접근 범위

Codex CLI는 요약에 필요한 임시 로그 파일만 참고하도록 설계한다.

- 홈 디렉터리 탐색
- 시스템 설정 파일 분석
- 다른 Discord 로그 조회
- Git 저장소 수정
- 파일 생성 및 코드 수정

본 작업에서 Codex의 역할은 **텍스트 요약기**이다.

# 42. 동시 실행

동일 채널에서는 동시에 두 개 이상의 요약을 실행하지 않는다.

서로 다른 채널에서 동시 요청이 발생한 경우에는 다음 두 방식 중 하나를 구현할 수 있다.

1. 채널별 병렬 실행
2. 전역 Codex 작업 큐

초기 구현은 안정성을 위해 전역 Codex 작업 수를 제한하는 것을 권장한다.

# 44. `!!요약좀 도움`과 쿨타임

`!!요약좀 도움`은 요약 작업이 아니므로 요약 쿨타임과 관계없이 언제든 사용할 수 있다.

요약 진행 중에도:

```text

```

은 정상 응답한다.

또한 `!!요약좀 도움` 실행 자체가 1분 또는 5분 쿨타임을 발생시키지 않는다.

# 53. 정상 동작 판정 기준

다음 조건을 만족하면 기본 기능이 정상적으로 구현된 것으로 판단한다.

## 채널 설정

- `/채널 설정`으로 서버별 주시 채널 선택 가능
- 선택된 채널만 실시간 SQLite 캐시
- 설정은 봇 재시작 후에도 유지
- 주시하지 않는 채널에서는 `!!요약좀` 실행 차단
- 주시 해제 후 새 메시지는 캐시하지 않음
- 새로 주시한 채널에서 과거 범위가 필요하면 Discord History로 보충 가능

## 명령

- `!!요약좀` 입력 시 최근 1시간 수집
- `!!요약좀 3` 입력 시 최근 3시간 수집
- `!!요약좀 2시간` 정상 처리
- `!!요약좀 30분` 정상 처리
- `!!요약좀 100개` 정상 처리
- `!!요약좀 오늘` 한국시간 00:00부터 수집
- `!!요약좀 2일` 정상 처리
- `!!요약좀 1주` 정상 처리
- `!!요약좀 도움` 정상 출력

## 로그 필터

- 요약봇 메시지 제외
- 다른 봇 메시지 제외
- 자동화 메시지 제외 권장
- 현재 요약 명령 메시지 제외
- 일반 사용자 메시지만 Codex 입력에 포함

## SQLite 캐시

- 일반 사용자 메시지를 SQLite에 캐시
- 메시지 캐시 최대 7일 보존
- 7일이 지난 메시지 자동 삭제
- Discord Message ID 기반 중복 방지
- 동일 또는 겹치는 요약 범위에서 기존 캐시 재사용
- 캐시에 없는 시간 구간만 Discord History에서 추가 조회
- 채널별 수집 완료 범위 메타데이터 관리 권장
- `X개` 요청 시 DB에 부족한 개수만 추가 수집
- DB 장애 시 가능한 경우 Discord History 직접 조회로 fallback

## 요약

- SQLite에서 요청 범위 메시지 조회
- Codex 입력용 임시 파일 생성
- Codex CLI가 임시 파일을 읽음
- 요약 작업 종료 후 임시 파일 삭제
- GPT-6 Luna Light 사용
- 화자별 발언 내용 식별
- 주요 결정 및 미해결 사항 정리
- 없는 내용 생성 금지
- 자연스러운 한국어 하오체 사용

## 출력

- 명령을 실행한 동일 채널에 결과 게시
- `XX부터 지금까지의 요약이오.` 머리말 사용
- 길 경우 Discord 제한에 맞춰 분할

## 쿨타임

- 요약 처리 중 중복 실행 차단
- 처리 중 호출 시 `요약중이오. 좀 기다리시오.`
- 성공 후 5분 동안 재실행 차단
- 성공 쿨타임 중 `아직은 때가 아니오. 00분 00초 뒤에 오시오.`
- 요약 실패 시 성공 쿨타임 미적용

# 55. 최종 요약

**신창섭이 요약을 정상화하네**는 Linux LXC에서 동작하는 Discord 채널 전용 요약 봇이다.

서버 관리자는 `/채널 설정`을 통해 봇이 주시할 Discord 채널을 선택한다. 봇은 설정된 채널의 일반 사용자 메시지만 SQLite에 실시간 캐시하며, 캐시는 최대 **7일간** 유지한다.

사용자가 주시 대상 채널에서 `!!요약좀`을 입력하면 현재 채널의 대화를 설정된 범위만큼 수집한다.

이전에 수집한 기간과 새로운 요약 요청 기간이 겹치는 경우 SQLite에 존재하는 메시지를 재사용하고, 캐시에 없는 구간만 Discord History에서 추가 조회한다.

최종 요청 범위는 SQLite에서 조회하여 Codex 입력용 임시 파일로 생성한다. 이 파일을 Codex CLI의 **GPT-6 Luna Light**에 전달하여 요약하며, 결과에서는 주요 주제뿐만 아니라 **어떤 사용자가 어떤 이야기를 했는지**를 명확하게 드러낸다.

Codex 입력용 임시 파일은 요약 작업이 끝난 뒤 삭제하며, 장기 재사용은 SQLite 메시지 캐시가 담당한다. SQLite 메시지 캐시는 생성 시점과 관계없이 메시지 작성 시각 기준 최대 **7일**까지만 유지한다.

봇의 안내 및 요약 문체는 일관되게 자연스러운 `-하오체`를 사용한다.

기본 요약 범위는 최근 1시간이며 다음 옵션을 지원한다.

```text
!!요약좀
!!요약좀 X
!!요약좀 X분
!!요약좀 X시간
!!요약좀 X개
!!요약좀 오늘
!!요약좀 X일
!!요약좀 X주
```

도움말은 다음 명령으로 확인한다.

```text
!!요약좀 도움
```

요약 처리 중에는 중복 작업을 차단하고:

```text
요약중이오. 좀 기다리시오.
```

라고 안내한다.

요약 성공 후에는 5분 동안 새 요약 실행을 제한하며:

```text
아직은 때가 아니오. 00분 00초 뒤에 오시오.
```

라고 안내한다.

최종 결과는 다음 형태로 현재 채널에 게시한다.

```text
XX부터 지금까지의 요약이오.

(요약 내용)
```

이 문서를 기준으로 Discord 메시지 수집부, SQLite 캐시 관리부, 캐시 범위 계산부, 임시 파일 관리부, Codex CLI 실행부, 명령 파서, 쿨타임 상태 관리부를 각각 구현하면 된다.
