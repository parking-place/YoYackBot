# 1.0.0-P4 — 운영 배포·동일 SHA smoke·초기 관측

- 상태: **PUSH_PENDING**
- 명세 근거: §3–5, §13, §23–29, §53
- 검증 ID: `T100-P4-A`, `T100-P4-B`
- 검증 환경: **OPS** — LXC의 서비스·장애·자원·복구 검증. 운영 변경은 그 단계 실행 시 확인된 대상과 범위에서 수행한다.

## 선행 조건

[1.0.0-P3](../1.0.0/03-rollback-rehearsal.md)가 검증과 GitHub push 확인까지 끝나 DONE이어야 한다.

## 수행 작업

1. 확인된 실행 범위 안에서 검증된 1.0.0 후보 SHA를 배포하고 신규 작업 수락 전 설정·인증·DB 준비 상태를 확인한다.
2. 허용한 검증 채널에서 설정·기본/개수/오늘·도움말·겹침 재사용·중복 차단·성공 cooldown을 smoke로 확인하도록 계획했다. [사용자의 후속 결정](POSTING_WAIVER.md)에 따라 새 배포의 실제 응답·게시 확인을 출시 필수 게이트에서 제외하고 `SKIPPED_BY_USER`로 기록한다.
3. [사용자 결정](../DURATION_WAIVER.md)에 따라 24시간 관측을 생략한다. 배포 직후 자원·실패·임시파일/TTL·복구 준비를 점검하고, 실패하면 검증된 복귀 절차로 돌아가 증거를 남긴다.

## 산출물

배포 SHA, 운영 smoke와 즉시 점검, 24시간 관측 생략 또는 실패/롤백 기록.

산출물은 앞으로 구현할 대상이다. 이 계획 파일을 작성한 것만으로 산출물이 구현되었다고 판단하지 않는다.

## 검증과 통과 기준

- [ ] `T100-P4-A`: 실행 중 버전/SHA가 후보와 일치하고 실제 게시까지 성공한 요청에서만 cooldown이 적용된다. 새 배포의 실제 게시·cooldown은 확인되지 않았으므로 [사용자 결정](POSTING_WAIVER.md)에 따라 `SKIPPED_BY_USER`로 남긴다.
- [x] `T100-P4-B`: 배포 직후 상태·자원·보존 점검이 정해진 기준을 충족하고 출시 차단 결함이 생기면 1.0.0-P5로 진행하지 않는다. 24시간 가용성은 미검증이다.
- [x] 영향받는 선행 기능의 회귀와 미실행·실환경 미확인 항목을 증거에서 구분했다.

## 단계 완료 — GitHub 업로드 필수

- [ ] 위 작업·검증을 완료하고 [증거 양식](../EVIDENCE_TEMPLATE.md)에 대상 SHA·환경·결과·제한을 기록했다.
- [ ] 실제 비밀값·`.private`·DB·Discord 원문·임시 파일이 커밋에 없음을 확인했다.
- [ ] 구현과 증거를 단계별로 commit하고 대상 브랜치에 **GitHub push**했다.
- [ ] 원격에서 증거 커밋 존재와 구현 SHA 포함, 필요한 CI 결과를 확인했다.
- [ ] [STATUS](../STATUS.md)를 DONE으로 갱신한 종료 커밋도 push하고 마지막 원격 반영을 확인했다.

**push 실패 또는 원격 확인 미완료는 PUSH_PENDING이며 단계 완료가 아니다.** 상세 절차와 SHA 기록 방식은 [GIT_WORKFLOW](../GIT_WORKFLOW.md)를 따른다.

## 실패 및 다음 단계

검사 실패 시 실패 사례·환경·복구 방법을 증거에 남기고 IN_PROGRESS/BLOCKED로 유지한다. 수정 후 영향 검사를 다시 수행하며 완료 전에 의존 단계로 넘어가지 않는다.

이 단계의 마지막 원격 반영까지 확인한 뒤 다음으로 진행한다: [1.0.0-P5](../1.0.0/05-release-publish.md).
