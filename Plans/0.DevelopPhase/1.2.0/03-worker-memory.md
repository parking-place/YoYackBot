## 선행 조건

P2의 종료 D와 캐시 정합성 회귀를 확인한다. B05는 retry-state 저장 오류를 주입한 worker 종료 재현이며 실제 디스크 장애 실험은 아니다. B08은 정적 확인뿐이므로 입력 초과 예외뿐 아니라 읽은 행 수와 메모리를 이번 단계에서 측정한다. 실제 모델·Discord·운영 DB 없이 수행한다.

## 한정 부하의 실행 전 고정안

아래 값은 **미실행 제안 기준**이며 성능 달성 주장이 아니다. 구현 시작 시 LXC 여유 자원을 확인하고 증거에 최종 기준을 먼저 고정한다. 변경이 필요하면 이유·새 값을 실행 전에 기록하며 실패 결과를 통과시키려고 사후 완화하지 않는다.

- 입력 예산 `4 MiB`, batch 최대 `128행`, 합성 본문은 행마다 ASCII `256바이트`로 고정한다. 동일 기간·채널의 `100,000행`과 `1,000,000행` 두 DB로 전체 자료량만 10배 바꾼다. 두 경우 모두 입력 예산을 훨씬 초과한다.
- DB 생성은 측정 프로세스 밖에서 끝낸다. 각 조회는 별도 새 프로세스에서 같은 런타임·SQLite 설정으로 실행하며 시작 RSS와 peak RSS를 모두 기록한다. SQLite page cache의 제한도 동일하게 고정하고 자료 생성 비용과 조회 비용을 섞지 않는다.
- 각 크기 3회, 총 **6회**로 제한한다. 조회당 timeout은 `60초`, 프로세스 메모리 상한은 `512 MiB`, 합성 DB 관련 디스크 상한은 `2 GiB`로 제안한다. 상한 도달은 실패/중단으로 기록하고 무한 반복하지 않는다.
- 합격 제안값: 읽은 행 수는 각 회 `ceil(4 MiB / 256) + 2 × 128 = 16,640행` 이하이고 10배 DB에서도 같은 상한을 지킨다. 이는 허용 최대치이며 메타데이터 예산 때문에 더 일찍 멈출 수 있다.
- peak RSS는 각 회 `256 MiB` 이하이고, 동일 측정 조건에서 100만행의 중앙값은 10만행 중앙값보다 `32 MiB` 이상 증가하지 않는다. 각 회의 시작 RSS도 함께 비교해 interpreter 초기화 변동을 구분한다. 총 DB 크기에 비례하는 materialization이 있으면 최종 예외가 맞더라도 실패다.

## 실패 경계

- retry-state 쓰기가 실패해도 다른 채널과 전체 loop가 연쇄 종료되지 않는다. DB가 복구되면 backoff 뒤 진행하고 실패 중에는 진척을 꾸며 내지 않는다.
- budget 초과를 정상적인 일부 요약으로 바꾸지 않는다. DB cursor·슬롯·임시 파일은 오류/취소 때 정리하며 바쁜 재시도로 CPU를 소모하지 않는다.
- 단순 tracemalloc 수치나 `ConversationTooLarge` 발생만으로 B08을 닫지 않는다. 실제 프로세스 peak RSS·읽은 행 수·유한 종료를 함께 제시한다.
