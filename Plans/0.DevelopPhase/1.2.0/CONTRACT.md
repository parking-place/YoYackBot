# 1.2.0 버그 수정·F02·F10 계약

2026-10-02 사용자 요청에 따른 **구현 목표**다. 근거는 [감사 결함 B01~B14](../../1.Improvements/02-bug-findings.md)와 [기능 F02·F10](../../1.Improvements/05-feature-proposals.md)이다. 현재 제품 PASS를 뜻하지 않는다.

## 1. 범위와 유지할 동작

- B01~B14 전체를 수정한다. 그 외 구조·공급망·문서 개선 제안은 이 결함 수정과 두 기능에 직접 필요한 범위만 반영한다.
- 신규 기능은 F02·F10 두 가지다. F01·F03~F09는 채택하지 않는다.
- 한국어 하오체·기존 요약 밀도·추가 요청·기본 1분 성공 쿨타임·같은 채널 요약 게시·현재 모델과 동시 실행 한도를 유지한다. 호출 상한은 현행 최대 3회로 유지한다.
- `/말투`, 답장에 따른 범위 변경, 평가 후보 10개·심사·최근 평가 20개·최대 5회 호출은 **1.3.0**에만 있다.
- 원문·인증값·실제 서버/사용자 식별값을 공개 문서·로그에 기록하지 않는다. 아래 기능 예시와 시험 자료는 합성값이다.

## 2. B01·B02·B09·B14: 권한과 설정

### 기존 채널 목록의 안전한 전달(B01)

- 기존 `!!요약좀 채널` 문법·주시 채널에서만 응답하는 조건·요청자 기준 목록 필터를 유지한다. 목록 본문은 **요청자의 DM으로 전달**하고 공개 채널에는 개인정보 없는 성공 안내만 남긴다.
- DM이 불가능하면 공개 채널에는 “목록을 개인 메시지로 전달하지 못했소. DM 수신 설정을 확인하시오.”와 같은 일반 안내만 보낸다. 이름·ID·목록 개수·숨은 채널의 존재를 공개 fallback에 포함하지 않는다.
- DM 각 조각 직전에 요청자의 현재 Guild 소속·채널 열람권한·주시 설정을 다시 검사한다. 권한이 바뀌면 재필터링하거나 중단한다. 멘션·embed는 계속 억제한다.
- DM에서 새 요약 명령을 받거나 요약 본문을 DM으로 보내는 기능은 추가하지 않는다. 새로운 조회 슬래시 명령·운영 화면(F01)도 만들지 않는다. 변경 목적은 기존 목록 명령의 B01 해소다.

### 관리 역할의 원자성(B02·B14)

- Discord 역할 삭제는 단일 트랜잭션에서 해당 역할만 제거하고 revision을 갱신한다. 또는 같은 원자성을 보장하는 CAS 재시도를 사용한다. 오래된 전체 집합으로 덮어쓰지 않는다.
- 오프라인 동안 사라진 역할은 설정을 열거나 저장할 때 안전하게 정리한다. 현재 존재하는 역할·동시에 추가/해제한 관리자 변경은 유지한다.
- 삭제된 ID 정리 사실을 설정 화면에 알리고, 권한 재검사·화면 소유자·만료·동시 수정 감지를 유지한다. 존재하지 않는 역할 때문에 전체 해제만 가능한 상태를 만들지 않는다.

### UI와 DB 대기(B09)

- SQLite snapshot·쓰기·권한 저장소 조회를 이벤트 루프에서 동기 실행하지 않는다. DB 접근 전에 응답을 defer하고 thread/비동기 어댑터에서 실행한다.
- 저장 직전 권한·주시·revision을 재확인한다. 데이터 쓰기는 성공했으나 화면 응답만 실패한 경우 저장 상태와 오류 안내가 어긋나지 않도록 한다.

## 3. B03·B04·B06·B07: 캐시 정합성과 보존

- **생성 공백 보충과 기존 메시지 수정·삭제 대조를 모두 수행한다.** Gateway 시작·재접속 시 보관기간 안의 검증 필요 구간을 기록하고 현행 `CacheOnlyCollector/build_workflow`가 그 상태를 실제로 사용한다.
- 정상적으로 끝까지 조회한 구간만 원자적으로 reconcile한다. 부분 페이지·403·429·timeout·DB 실패를 “원문 없음”으로 간주해 삭제하거나 ready로 처리하지 않는다.
- reconcile 중 live edit·delete와 경합하면 최신 수정 시각과 tombstone을 보존한다. 오래된 History 페이지가 최신 본문·삭제를 되돌리지 못해야 한다.
- history·overlap·ready 중 어느 단계에서 재단절/재시작해도 새 공백을 누적한다. 고정된 과거 `finished_us` 이후부터 현재 연결 경계까지의 미검증 구간이 남으면 요약 준비 완료로 표시하지 않는다.
- 모든 fetch·upsert·raw/cached edit·백필 재개에 동일한 **현재 시각 기준 retention cutoff**를 적용한다. 설정은 1~30일이며 기간 축소·장기 중단 후 재개도 반영한다.
- raw update도 수정 시각의 단조성을 지킨다. 동일 timestamp는 멱등 처리하고, timestamp가 없거나 과거인 이벤트가 최신 확정 본문을 덮어쓰지 않도록 정책을 고정한다. 모호한 경우 제한된 재검증으로 해소한다.
- 재검증의 조회량·동시 실행은 기존 bounded History 체계에서 관리한다. 끝나지 않은 구간을 조용히 제외해 완전한 요약으로 게시하지 않는다.

## 4. B05·B08: worker 수명과 입력 한도

- 페이지 처리뿐 아니라 `defer/block` 저장 실패도 격리한다. 채널 한 개의 오류가 전체 백필 loop를 종료하지 않게 하며 DB 복구 후 backoff를 거쳐 재개한다.
- worker의 예기치 않은 종료는 감지·재생성하거나 명확한 비정상 상태로 표시한다. 종료 요청의 `CancelledError`는 삼키지 않고 작업·슬롯·파일을 정리한다.
- 시간형 수집은 cursor batch를 읽으며 누적 원문 크기·레코드 예산을 검사한다. 전체 `fetchall()` 이후 제한하는 방식을 없앤다. 초과 시 명확히 실패하고 잘린 입력으로 정상 요약하지 않는다.
- 바이트 상한은 JSONL 메타데이터와 F10 참조 추가분을 포함한 최종 직렬화에도 적용한다. 메모리 제한의 검증 기준은 [P3](03-worker-memory.md)에 있다.

## 5. B10~B13: 출력과 모델 실행 계약

- 화자 위치의 Markdown을 정규화한 뒤 내부 P1 등의 키를 검사한다. 정상 인용·코드까지 일괄 차단하지 않는다. F10의 요청별 메시지 키도 최종 사용자 출력에 노출하지 않는다.
- 평가·거절 고지 등 부속 문구를 분리한 **실제 요약 본문**이 비어 있으면 성공 결과·게시·성공 쿨타임을 만들지 않는다. 한정 재시도 또는 `OUTPUT_INVALID`로 처리한다.
- 최초 생성·본문 재시도·평가 재생성·평가 생략·최종 합성에 같은 핵심 검증을 적용한다. 평가만 불량하면 검증된 본문을 살리고 평가를 생략한다. 불량한 본문은 게시하지 않는다.
- 기본 `codex` 이름은 시작 시 PATH에서 검증된 절대 실행 경로로 해석하고 고정한다. 누락·비실행 파일·버전 불일치를 준비 단계에서 분류한다. runner와 사용량 조회는 같은 해석 결과를 사용한다.
- 모델 파일 형태 확인과 실제 인증 성공을 구분한다. 이번 bugfix를 이유로 실제 모델 검사를 health마다 호출하지 않는다.

## 6. F02: 현재 채널의 수집 진행·차단 원인

### 노출 위치와 동작

- **기존 `!!요약좀 상태`의 현재 채널 구역**과 수집 미완료 안내에만 추가한다. 새 명령·대시보드·외부 자동 알림은 없다.
- 요청한 현재 주시 채널의 단계·처리 페이지 수·현재 저장 메시지 수·마지막 진척 시각·차단 이유·다음 재시도 시각을 제공한다. 다른 채널 이름·ID·진행 상태·숨은 채널 수는 추가하지 않는다.
- 단계는 최초 History 수집, 연결 공백/수정·삭제 대조, 재시도 대기, 권한 등으로 차단, 준비 안내 대기, 요약 가능으로 구분한다. 요약 가능은 기존 `summary_ready`와 B03/B04의 검증 경계가 모두 충족된 상태다.
- 첫 준비 안내 전송 실패 시 phase가 ready여도 “요약 가능”으로 표시하지 않는다. worker 종료·진척 중단은 정상 수집 중으로 오인시키지 않는다.
- 전체량을 모르면 “현재 저장 N건 / 처리 P페이지”만 보여 준다. 근거 없는 백분율·100%·ETA는 표시하지 않는다. 데이터 읽기 실패는 0건이 아니라 확인 불가다.

### 상태 데이터

- 선택 테이블 `backfill_progress`를 `(guild_id, channel_id, token)` 세대와 연결한다. 작업 종류/회차, 성공 commit 페이지 수, 마지막 진척 시각 등을 가진다.
- 페이지·cursor commit과 같은 트랜잭션에서 진척을 갱신한다. 실패·재시도·stale page는 중복 합산하지 않는다. 같은 token에서 새로운 접속 공백 점검을 시작하면 회차를 구분한다.
- “현재 저장 메시지 수”와 “이번 작업에서 처리한 수”의 의미를 섞지 않는다. 업그레이드 전 누계를 추측하지 않고 확인 불가로 표시한다.
- 주시 해제·채널 삭제·서버 탈퇴 때 정리한다. 설정 백업에 넣지 않는다. 로그는 고정 상태·수치·시간만 허용하며 원문·채널명·예외 문자열은 제외한다.

## 7. F10: 선택 범위 안의 답글 관계

### 수집과 저장

- `is_reply`는 유지하고 nullable `reply_to_message_id`를 도메인에 추가한다. Gateway와 정상 History 수집에서 같은 Guild·채널임을 확인한 참조 ID만 저장한다.
- 선택 테이블 `message_reply_refs`에 source 메시지·대상 메시지 ID, Guild/channel, 관측 시각·원문 revision 정보를 저장한다. 원문 본문을 복제하지 않는다.
- 참조 대상 본문을 별도로 fetch하거나 다른 채널을 탐색하지 않는다. 기존 캐시의 boolean만으로 대상 ID를 복원하지 않고 미확인으로 유지한다. 정상 재수집·관측에서 자연스럽게 채운다.

### 모델 입력과 결과

- 최종 선택 집합 안의 메시지에 요청별 `M1`, `M2` 등 익명 키를 부여한다. 대상이 동일 집합 안에 있을 때만 `reply_to: "M1"`을 전달한다.
- 범위 밖·삭제·필터 제외·다른 채널·미확인 대상은 `is_reply=true`와 참조 없음으로 처리한다. 참조가 있다고 원문에 없는 주장·동의·결론을 보충하지 않도록 프롬프트에 명시한다.
- 원시 Discord ID·URL은 모델 입력·로그·요약문에 추가하지 않는다. 원문 링크 기능(F04), 범위 자동 확장, 요약 명령의 답장 기준 범위(1.3.0)는 구현하지 않는다.
- 새 모델 호출 단계를 추가하지 않는다. 동일 입력에서 관계 정보를 더하는 것이며 호출 상한은 현행 3회다.

### 정리와 경합

- 메시지 삭제 시 그 메시지의 참조 행과 해당 메시지를 향한 참조를 함께 제거/무효화한다. retention·주시 해제·서버 탈퇴·reconcile에도 동일 원칙을 적용한다.
- 오래된 History/raw edit가 최신 참조를 되살리지 않도록 원문 revision·삭제 상태를 확인한다. 전송할 집합을 확정할 때 다시 참조 유효성을 확인한다.
- 참조 메타데이터는 캐시이며 설정 백업에서 제외한다. 과거 요약·관계의 장기 아카이브를 만들지 않는다.

## 8. DB·업그레이드·복귀

- 현재 필수 `schema 5`와 기존 `messages` 레이아웃을 유지하고 F02/F10은 선택 테이블을 사용한다. 새 테이블이 없는 DB·빈 설정 복원 DB도 정상 시작해야 한다.
- 기존 연결에 FK 활성화가 보장되지 않으므로 삭제 정리를 FK cascade에만 의존하지 않는다. DB trigger 또는 동등한 검증된 정리 정책으로 구버전 writer의 삭제·편집에도 메타데이터를 삭제/무효화한다.
- 새 테이블이 있는 상태에서 `v1.1.3a`로 복귀해 생성·편집·삭제·정리하고 다시 1.2.0으로 올리는 격리 검증이 필요하다. 선택 테이블을 “무시하니 호환”이라고만 판정하지 않는다.
- 만약 이 방식으로 안전한 호환성을 확보할 수 없으면 schema 계약 변경을 별도 결정·문서화한 뒤 진행하며, 이미 1.3.0에 남긴 schema 5 가정도 함께 재검토한다. 이번 계획 단계에서는 schema 버전을 올리지 않는다.

## 9. 검증과 인수 경계

- 28개 검사는 전부 NOT_RUN에서 시작한다. 과거 감사의 1,178개 통과와 11건 재현은 문제를 정의하는 증거다.
- 실제 모델은 P6에서 합성 품질 사례 8건을 수행한다. 사례당 요약 요청 1회·요청당 내부 호출 최대 3회이며, 실패 수정 후 재검증은 횟수와 이유를 별도 기록한다. 실사용 원문을 fixture로 복사하지 않는다. 모델 호출 불가·한도 부족은 미실행으로 기록한다.
- P7에서 같은 후보 SHA의 전체 회귀·설정 백업/복원·복귀·배포 상태와 시험 Discord 사용자 확인을 기록한다. 미확인 검사를 PASS로 바꾸거나 새 기능 출시를 선언하지 않는다.
