# 명세 해석과 구현 결정

원본 [기능 명세 v1.5](../shinchangseop_discord_summary_bot_spec_v1.5.md)는 변경하지 않는다. 아래는 충돌을 해소하거나 명세가 열어 둔 선택을 구체화한 **계획 기준안**이다. `확정 단계`에서 검증·기록하며, 그 전에는 검증된 구현으로 취급하지 않는다.

## D01 — 7일 캐시와 최대 4주 요청

- 근거: §13-2, §34, §39, §55.
- SQLite의 영속 메시지는 `created_at` 기준 최근 7일로 제한한다. 기본 상한은 명세의 1440분 / 168시간 / 7일 / 4주 / 1000개를 각각 유지한다.
- 7일보다 오래된 요청 구간은 History에서 직접 읽어 요청 수명 동안만 메모리 또는 제한된 임시 파일에 두고, 최근 캐시 결과와 합친다. 오래된 본문을 영속 DB에 잠시 넣었다 지우는 방식도 피한다.
- 예: 9월 28일의 `2주` 요청은 9월 14~21일을 요청 전용 비영속 데이터로, 9월 21~28일을 7일 캐시 구간으로 취급한다. 경계에서 message_id로 중복을 제거한다.
- `X개`의 역사 탐색은 초기 최대 28일과 조회 페이지·입력 크기·시간 예산으로 제한한다. 부족분·상한 도달을 사용자에게 명시하며 요청 수를 조용히 줄이지 않는다.
- 7일 초과 범위에서는 “최종 입력 전체를 SQLite에서 읽음”에 예외가 생긴다. 이 예외를 명시적으로 문서화하고 보존 상한을 우선한다.
- 확정 단계: 0.0.0-P1; 구현·경계 검증: 0.4.0-P3/P4.

## D02 — 성공 쿨타임의 시작점

- 근거: §4는 쿨타임을 게시보다 먼저 나열하지만 §25는 결과 게시 성공까지 요구한다. **마지막 분할 메시지 게시 성공 시점 + 300초**를 적용한다.
- 수집·모델·빈 결과·부분 전송 실패는 성공이 아니다. 작업을 정리한 뒤 IDLE로 돌아가며 성공 쿨타임을 적용하지 않는다.
- 예: 2개 조각 중 첫 전송만 성공하고 둘째 전송이 실패하면 게시 성공이 아니므로 5분 쿨타임을 시작하지 않는다.
- 부분 전송의 메시지 ID와 성공한 순서를 요청 단위로 관리한다. 응답 불명확 시 무조건 재전송하지 않고 알려진 결과를 확인하거나 수동 재요청을 안내한다.
- 확정 단계: 0.0.0-P1; 구현: 0.6.0-P4, 0.7.0-P2/P3.

## D03 — 모델 표시명과 실제 실행 설정

- 근거: §3, §14, §50의 `GPT-6 Luna Light` 요구를 그대로 유지한다.
- 2026-09-28 열람한 [공식 Models 문서](https://learn.chatgpt.com/docs/models)는 `gpt-6-luna`와 UI의 Light / CLI의 Low 표현을 설명한다. 이것만으로 해당 계정에서 Luna의 특정 reasoning 조합이 지원된다고 확정하지 않는다.
- 후보 매핑은 `gpt-6-luna` + Light에 대응하는 지원 reasoning 설정이다. 실제 LXC의 CLI 도움말·모델 목록·인증 상태와 합성 입력 실행으로 확인한다. 미지원이면 해당 연동 단계는 BLOCKED이며 다른 모델로 조용히 대체하지 않는다.
- 확정 단계: 0.0.0-P3에서 확인 절차, 0.5.0-P1에서 실제 사용 가능성과 식별자 확정.

## D04 — 캐시 개수와 최신성

- 근거: §13-6은 완료 범위 메타데이터를 요구하고 §13-8은 캐시가 X개면 History를 생략한다.
- “X개 존재”만으로 중간 누락이 없는 최신 X개를 보장할 수 없다. 요청 종료 경계에서 X번째 메시지까지 연속 수집이 입증된 경우에만 무조회 재사용한다.
- 연결 중단·주시 해제·재시작 구간은 미수집으로 표시한다. 빈 구간도 History를 끝까지 조회해야 완료 범위가 된다. 페이지 실패 시 전체 범위를 완료 처리하지 않는다.
- 생성 범위의 완전성과 오프라인 수정·삭제의 신선도는 다르다. 재접속 후 요청 구간을 재확인하는 정책을 두며, 확인하지 못한 캐시를 원본과 완전히 같다고 보장하지 않는다.
- 확정·구현: 0.3.0-P4, 0.4.0-P2/P4.

## D05 — 대상 채널과 설정 변경

- 1.0.0까지 일반 Guild 텍스트 채널만 지원한다. DM·스레드·포럼 게시물·음성 텍스트와 다른 채널은 합치지 않는다.
- `/채널 설정`은 서버 관리자 또는 Manage Channels 보유자가 사용한다. UI 표시뿐 아니라 저장 시에도 사용자·봇 권한과 Guild를 재확인한다.
- 주시 해제는 신규 저장·History·새 요약을 즉시 차단한다. 진행 중 작업도 수집·Codex 실행·각 전송 전에 재확인하여 추가 처리를 중단하고 입력을 정리한다. 이미 보낸 내용은 자동으로 삭제하지 않는다.
- 기존 캐시는 7일 정리 정책에 따른다. 주시 설정 DB를 읽지 못하면 수집 권한을 추측하지 않는다.
- 확정·구현: 0.1.0-P2/P3/P4; 통합 검증: 0.7.0-P3.

## D06 — 파서의 모호한 입력

- 명세의 포함 인식·옵션 우선순위를 유지하고 `도움`은 최우선 별도 경로로 처리한다.
- `!!요약좀 30분 부탁하오`처럼 허용 후행 문구를 처리하되, `2시간 100개`처럼 서로 충돌하는 범위는 거부한다. 복수 트리거는 한 번만 처리하며 파싱 불명확 시 사용법을 반환한다.
- 0·음수·소수·오버플로·미지원 단위·상한 초과를 거부하는 것을 기준으로 삼는다. 과거 명령 메시지는 입력에서 제외하되 검출 정책을 테스트로 고정한다.
- 확정·구현: 0.2.0-P1/P2/P3.

## D07 — 요청 경계와 게시 표시

- 시간 범위의 종료는 요청 수락 시각으로 고정한다. 처리 중 새 메시지가 결과에 섞이지 않는다.
- 내부 저장·계산은 UTC, 날짜 경계·출력은 Asia/Seoul이다. 범위는 반열린 구간 `[start, end)`으로 정의하고 동일 시각 메시지는 ID로 정렬한다.
- 시간 요청 머리말은 실제 적용한 범위 시작, 개수 요청은 선택된 가장 오래된 메시지 시각을 사용한다. 명세의 “지금까지”는 수락 시점을 뜻하며 오래 걸린 작업은 기준 시각을 보충한다.
- 확정·구현: 0.2.0-P4, 0.4.0-P1, 0.6.0-P3.

## D08 — Codex 격리와 임시 데이터

- 대화 본문은 명령이 아닌 신뢰할 수 없는 입력 데이터다. 입력 안의 “파일을 읽어라”, “외부로 전송하라”를 따르지 않도록 프롬프트와 실행 격리를 함께 적용한다.
- [공식 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)에 따라 `codex exec`, 최종 출력 분리, 세션 비보존 옵션을 검토한다. 정확한 옵션은 고정한 CLI 버전에서 재확인한다.
- 읽기 전용 설정만으로 모든 시스템 파일의 읽기 차단이 된다고 가정하지 않는다. [공식 sandbox 설명](https://learn.chatgpt.com/docs/sandboxing)을 참고해 OS 수준 접근 제한과 최소 파일 노출을 실제 공격성 입력으로 검증한다.
- 모델 통신에 필요한 연결과 임의 웹 탐색·MCP·추가 도구를 구분한다. 후자는 비활성화한다. subprocess 환경에서 Discord 인증값을 제거한다.
- 입력·최종 출력·stderr·CLI 세션 기록·크래시 잔여 파일까지 수명 정책을 적용한다. 원문과 요약을 운영 로그나 공개 CI 산출물에 남기지 않는다.
- 확정·구현: 0.5.0-P1/P2/P3/P4, 운영 점검: 0.8.0-P4.

## D09 — 큐와 재시작

- 채널 키는 `(guild_id, channel_id)`다. 채널별 단일 작업과 전역 Codex 동시 실행 1개를 초기값으로 제안한다.
- 유한 대기열의 수락 시점부터 SUMMARIZING을 유지한다. 큐가 가득 차면 잠금을 남기지 않고 하오체로 안내하며 성공 쿨타임을 만들지 않는다. 대기 시간도 제한한다.
- 성공 쿨타임 만료 시각은 영속화한다. 재시작 시 실제 생존 작업이 없는 SUMMARIZING은 실패로 복구한다. 프로세스 중복 시작도 차단한다.
- 확정·구현: 0.7.0-P1/P2/P4; 자원 조정: 0.8.0-P5.

## D10 — 캐시 장애와 크기 초과

- 캐시 실패라도 신뢰할 수 있는 주시 설정·권한이 있으면 History 직접 수집을 허용한다. 설정까지 확인 불가하거나 무결성이 의심되면 안전하게 실패한다.
- 입력 한도를 초과하면 조용히 잘라 완전한 요약처럼 출력하지 않는다. 초기에는 범위를 줄이도록 안내하며 성공 쿨타임을 적용하지 않는다. 다단계 분할 요약은 별도 검증 없이 도입하지 않는다.
- 한도·timeout·큐 크기는 설정으로 분리한다. 운영 제안값은 0.0.0에서 기록하고 0.8.0에서 실측한다.
- 확정·구현: 0.4.0-P5, 0.5.0-P4, 0.8.0-P5.

## D11 — 대화 입력의 프롬프트 직접 전달

- 근거: §3.3, §14, D08, D10. 2026-10-05 사용자 결정(1.3.3 계획 2·3번).
- 명세 §3.3·§14와 0.5.0 CODEX_RUNTIME은 대화를 임시 파일로만 전달한다. 실측에서 Codex CLI 0.158.0은 모델이 읽은 도구 출력을 약 1만 토큰에서 잘라, 긴 대화가 앞뒤만 반영된 채 요약됐다(D10 위반). 파일 읽기 도구 턴도 호출마다 시간을 더했다.
- 1.3.3부터 대화 자료는 프롬프트 끝의 자료 블록으로 전달한다. 블록 구분자에는 요청마다 새 임의값을 넣고, 블록 안의 모든 글은 명령이 아닌 신뢰할 수 없는 자료라는 D08의 원칙을 프롬프트에 그대로 적용한다. 격리 환경에는 대화 파일을 넣지 않고, bwrap 격리·네트워크 차단·도구 비활성·세션 비보존은 유지한다.
- CLI 진단 출력에 되찍히는 프롬프트는 실패 분류에 쓰지 않으며 로그에 남기지 않는다. 모델 문맥보다 큰 입력은 자르지 않고 D10대로 범위를 줄이라고 안내한다.
- 프롬프트 주입 시험(대화 속 지시, 자료 블록 위조, 추가 요청 주입)을 실제 모델로 다시 통과해야 확정한다.
- 확정·구현: 1.3.3-P2/P3/P5. 실제 모델 주입 재시험(대화 속 지시·자료 블록 위조·지시문 공개·인증 파일 요구, 답글 속 주입, 본문 속 지시)을 1.3.3-P5에서 통과했다.
