# 1.0.0b-1 — 대량 요약 복구와 30일 초기 수집

상태: **P1·P2 완료, P3 진행 중, P4~P6 계획**. 선행: 출시 완료한 [1.0.0a](../1.0.0a/README.md). 이 계획은 [폐기된 1.0.0b](../1.0.0b/README.md)를 대체한다. 옛 P1의 진단 증거와 P2의 후보 코드는 검토 입력으로 보존했으며, 새 단계는 별도 C/E/D 검증으로 완료한다.

100건을 넘는 요약에서 관측된 모델 오류·대기열 만료를 분리해 고친다. 동시에 **수집 메커니즘을 변경한다**. 새 주시 채널은 처음 한 번 조회 가능한 최근 30일 이내 일반 사용자 기록을 끝까지 초기 수집한다. 그때부터 들어오는 새 메시지는 Gateway 실시간 경로로 DB에 저장하고, 초기 수집 완료 뒤의 일반 요약은 **DB만 읽는다**. 일반 요약 요청마다 Discord History를 다시 뒤져 보충하지 않는다. 연결이 끊겨 생긴 누락은 별도 복구 작업으로 확인·보충한 뒤 정상 상태로 되돌린다. 보관 기간은 최대 30일이다. Discord의 삭제·권한 제한 때문에 조회 불가능한 기록까지 확보했다고 주장하지 않는다.

`첫 주시 → 최근 30일 전체 수집(실시간 저장 병행) → 수집 시작~완료 사이 재확인·중복 제거 → 준비 완료 → 실시간 저장 + DB 요약`이 정상 경로다. 업그레이드 전에 이미 주시하던 채널도 한 번 전체 수집해 같은 경로로 옮기되, 새 채널 전용 시작·완료 문구를 소급 게시하지 않는다.

처음 주시하는 채널에는 `안녕하시오. 요약을 위해 데이터 수집중이오.`를 보내고, 완전 수집 뒤 `이제부터 요약을 해줄 수 있을 것 같소.`를 보낸다. 초기 수집 중 `!!요약좀` 요약 요청에는 `참을성을 기르시오 아직 준비가 되지 않았소.`라고 답하며 요약 작업을 시작하지 않는다. `!!요약좀 도움`은 계속 사용 가능하다. 이 안내는 [1.0.2](../1.0.2/README.md)의 요청별 수집 안내와 별개다.

| 단계 | 목표 | 검사 | 상태 |
|---|---|---|---|
| [P1](01-large-input.md) | 대량 입력·모델 오류 검증과 수정 | B1A/B1B | DONE |
| [P2](02-backfill.md) | 첫 주시 전체 수집→실시간 DB 저장으로 전환 | B2A/B2B | DONE |
| [P3](03-readiness.md) | 시작·완료·준비 중 안내와 요약 차단 | B3A/B3B | PUSH_PENDING |
| [P4](04-queue.md) | 모델 대기열과 초기 수집의 시간 정책 | B4A/B4B | PLANNED |
| [P5](05-recovery.md) | 장애·중단·롤백 처리 | B5A/B5B | PLANNED |
| [P6](06-release.md) | 대량 요청·30일 수집 통합과 출시 | B6A/B6B | PLANNED |

각 단계는 구현 C, 같은 SHA의 개발 LXC 검증·증거 E, 종료 D를 **각각 commit·GitHub push**하고 원격 포함 관계와 필요한 CI를 확인해야 DONE이다. [공통 Git 규칙](../GIT_WORKFLOW.md), [검증 목록](TEST_MATRIX.md), [상태](STATUS.md)를 따른다. 실제 Discord 게시와 합성 시험을 구분한다. 8시간·24시간 연속 시험은 사용자의 요청에 따라 요구하지 않는다.

출시 이름/태그는 `1.0.0b-1` / `v1.0.0b-1`, Python 패키지 버전은 `1.0.0.2`로 한다. `v1.0.0b`는 만들지 않는다. [버전 대응표](../PATCH_VERSIONING.md)를 따른다.
