# 1.0.2 — 수집 시작·진행 중 범위 안내

- 상태: **PLANNED** (계획 문서 작성만 완료; 기능 구현·배포 전)
- 단계 수: **5단계**
- 선행 버전: [1.0.1](../1.0.1/README.md)의 실제 완료와 원격 증거. 현재 1.0.1도 PLANNED이므로 1.0.2 구현을 완료로 계산하지 않는다.

## 목표

주시 채널에서 유효한 요약 요청을 받아 **수집을 시작할 때** 요청 범위를 한 번 안내한다. 같은 채널에 요약 작업이 진행 중일 때 들어온 다음 요약 요청에는 새 요청의 범위가 아니라 **이미 진행 중인 작업의 범위**를 알려준다.

```text
!!요약좀 10일
10일 채팅을 요약해보겠소.
```

```text
현재 10일 분 채팅을 요약중이오.
참을성을 가져보시오.
```

현재 `YOYACK_MAX_DAYS` 기본값은 **7**이어서 `10일`은 거부된다. 첫 단계에 10일 허용과 실효 운영 설정 확인을 포함한다. 7일 SQLite 캐시 보존은 그대로 두고 7일 초과분은 기존 임시 History 수집 규칙을 따른다. [응답·상태 계약](NOTICE_CONTRACT.md)에 다른 범위, 예외, 중복 요청 경계를 명시했다.

[1.0.2 검증 목록](TEST_MATRIX.md)은 현재 전부 `NOT_RUN`이며 [1.0.2 상태](STATUS.md)는 전부 `PLANNED`이다. 계획을 GitHub에 게시한 것만으로 제품 단계가 끝나지 않는다. 각 단계는 구현·LXC 검증·증거 기록·**독립 commit → GitHub push → 원격 반영 및 필요한 CI 확인**을 마쳐야 DONE이다. 기존 [Git 완료 규칙](../GIT_WORKFLOW.md)의 C/E/D 절차를 따른다.

사용자가 앞서 생략한 8시간·24시간 연속 시험은 이 버전의 필수 게이트에 넣지 않는다. 실제 시험 Discord 게시 여부와 합성 검사 결과는 증거에서 구분한다. 제품 태그·Release는 배포 코드가 최종 게이트를 통과한 뒤에만 만든다.
